                                                 Abstract. We report on the verification of memory safety for decoder
                                                 components of liblzma, the compression library underlying xz-utils: the
                                                 LZMA2 state machine, the LZMA1 decoder it controls, the outer de-
                                                 coding path, and the shared sliding-window dictionary. Built with the
                                                 Verified Software Toolchain (VST), machine-checked body theorems es-

                                         liblzma, the compression library underlying xz-utils, is a widely used open-source
                                         dependency. The 2024 xz backdoor (CVE-2024-3094) [15] highlighted the trust
                                         placed in this codebase. While that attack used release and build machinery
                                         rather than a memory-safety defect, memory-safety defects are the largest single
                                         class of exploited vulnerabilities in C and C++ code, on the order of 70% of

serious issues at organizations such as Microsoft [14]. We therefore address the
library’s own code: whether decoder bodies can be proved safe under explicit
function contracts.
    The Verified Software Toolchain (VST) [4,7] supports foundational verifica-
tion of C programs through separation-logic proofs over CompCert semantics [12],
but the process remains labor-intensive. In our pipeline, AI agents construct and
repair proofs and may propose specification refinements. Humans approve every
change to a model or function specification before agents propagate it through
dependent proofs; the kernel of Rocq (formerly Coq)3 checks the resulting proof
terms. The liblzma case study examines both this division of labor and the proof
engineering needed to sustain it on production C.
    The reported decoder scope contains 22 VST body proofs closed through
Qed with no uses of admit or Admitted, covering the LZMA2 framing state
machine, outer decoding path, sliding-window dictionary, six supporting LZMA1
functions, and the LZMA1 decoding core. Each theorem establishes Clight safety
and model-relative partial functional correctness for its function body, assuming
the corresponding contract’s precondition and imported contracts. This safety
result rules out invalid memory accesses that the semantics represents as stuck
execution (§ 2.1); § 6 gives the inventory and contract boundary. The archived
artifact contains the Rocq/VST proof sources, verified liblzma source snapshot,
and build instructions [20].
    At 183,268 lines of proof script, the body proof for lzma decode is the largest;
§ 6 explains its scale. Verifiable C does not support the function’s original Duff’s
device4 control flow, so the verified 338-line C function uses an explicit state
machine; after CompCert preprocessing, its body spans 1,934 nonblank lines of C.
Proof construction spanned 1,595 agent sessions over 70 days (§ 3.2). Verification
also exposed source-level undefined behavior in the raw LZMA1 zero-input path:
range-decoder macros add zero to a null pointer and subtract two null pointers,
outside C’s defined pointer-arithmetic cases [11, 6.5.7] (§ 6).

2     Background

Interpreting the result requires a precise account of what a VST body theorem
guarantees and which decoder components it covers.


2.1    The Verified Software Toolchain

Separation logic extends Hoare logic with memory ownership. Its P ∗Q connective
requires disjoint footprints, while the frame rule preserves untouched state during
local reasoning [18]. These features support modular verification of pointer-rich
decoder structures.
    Verifiable C provides VST’s program logic and automation for Clight, Com-
pCert’s C intermediate language [4,7]. clightgen preprocesses and translates C
into a Clight abstract syntax tree embedded in Rocq. A function specification
(funspec) uses WITH for logical parameters, PRE for arguments and owned mem-
ory, and POST for return values and updated memory. Assertions such as data at
and field at link logical values to C objects and fields.
    A semax body theorem proves that one function body satisfies its funspec as-
suming the contracts in its global environment (Gprog). VST scripts use forward
symbolic-execution tactics5 such as start function, forward, forward if, and
forward call; entailer! handles entailments. The Rocq kernel checks the as-
sembled proof term.


Scope of body theorems. A verification scope names an entry point and enumer-
ates the in-project implementation functions whose bodies the result is intended
to cover; calls outside that set, such as library routines, are treated as imports.
§ 6.2 gives the scope for this case study and reports which individual body the-
orems are closed, i.e., proved through Qed with no uses of admit or Admitted.
Under the funspec precondition and imported contracts, a closed semax body
theorem establishes that execution cannot get stuck in the CompCert Clight
operational semantics. This rules out every run-time error that this semantics
represents as stuck execution, including memory faults; if the function returns
normally, its result satisfies the model-derived postcondition. Thus semax body
supplies Clight safety and model-relative partial functional correctness. It does
not by itself establish termination, total correctness, trace refinement, or com-
patibility between separately maintained caller and callee contracts.

2.2      The liblzma Library

Target selection. We initially considered several alternative C codebases, includ-
ing SQLite, Lua, Brotli, and others, but their size or reliance on features outside
VST’s supported C subset made them unsuitable. We encountered only a few
such features in liblzma; § 5.3 describes the required transformations.

Decoder structure. liblzma’s LZMA decoder interleaves an adaptive binary range
coder [19,17] with an LZ77-style dictionary [23]. The range coder reconstructs
bits that the LZMA state machine interprets as either a literal byte or a back-
reference (distance, length) into recently decoded output. That output is retained
in a fixed-size circular buffer (the sliding window ); a match copies bytes one at a
time modulo the buffer size, allowing its source and destination to overlap when
length > distance. The resulting proof obligations combine bit-level normaliza-
tion, overlapping copies, wrap-around indexing, and pointer arithmetic.

Scope. Figure 1 sketches the decoding path and the verified scope. The verified
portion spans three source files. In lzma2 decoder.c, it includes the LZMA2
framing state machine. In lz decoder.c, it includes the outer decoding path
and shared sliding-window dictionary. In lzma decoder.c, it includes six sup-
porting LZMA1 functions and the structured state-machine implementation of
the LZMA1 decoding core. The scope focuses on these decoder components and
excludes the container/stream layer (.xz parsing and integrity checks), the filter
framework, the index/metadata machinery, and all encoders.

3     The Agent-Driven Pipeline
Two requirements shape the pipeline: translation of build-configured C and hu-
man control over contract meaning.

3.1     Pipeline Overview
Model and Spec name stages in our workflow rather than VST artifact classes.
A functional Model gives executable Rocq definitions of a routine’s abstract
state and transition. For example, the LZMA2 model represents the current
framing phase, dictionary, and remaining input as Rocq values; lzma2 decode
maps an initial state to a return code and successor state. A Spec then adds VST
representation predicates that relate those values to C structs and buffers, and
a standard VST funspec whose postcondition requires the C outcome to agree
with the model. Proof agents then discharge the resulting body obligations by
symbolic execution and entailment solving. Humans review and approve the
models and funspecs; a proof failure may produce a proposed refinement, but it
returns through the same review gate rather than being applied by the proving
agent. The Rocq kernel checks the eventual proof term. This separation lets proof
search proceed autonomously while contract changes remain subject to human
review.
    Figure 2 shows build-aware Clight generation and model validation against
executions, detailed in § 5.1 and § 5.2.
    Human ownership was organized by artifact: model, specification, and body-
proof contributors reviewed changes to their respective stages against the C

bol interpretation coupled because probability updates depend on the LZMA

3.2     Coordinating Large Proofs

The cost of heavy proofs. The proofs in this development are unusually expen-
sive to check. A single funspec proof can run to thousands of lines of forward
symbolic execution, and elaborating one file can take hours and up to 20 GB
of RAM. At that scale the naive loop of editing a file and re-running coqc is
unworkable: every iteration pays the full cold-elaboration cost from the top of
the file. Working efficiently under these constraints imposes four requirements
that together shaped our tooling. First, iteration must be interactive, reusing the
already-checked prefix of a file so that only the tail past an edit is re-elaborated.
Second, the checking backend must stay alive, because every restart discards the
warm cache and forces a cold re-elaboration; restarts must therefore be rare and
narrowly scoped. Third, a backend that runs for a long time keeps using more
and more memory, so it must be able to free memory without throwing that
cache away. Fourth, a proof too large for one file or one agent’s context must
be decomposable across files that share a compiled load path. A bare coqc loop
provides none of these. Our Claude Code harness instead used the Model Con-
text Protocol (MCP) [1] to drive rocq-lsp through rocq-mcp; related MCP-style
tooling appears in [22]. Runs used Claude Code 2.1.218, under a combination of
a flat-rate subscription and metered API access, on one Ubuntu machine with
128 CPU cores and 1 TB of RAM, using Coq 8.20.16 and a project fork of VST
with its bundled CompCert front end.

MCP server. We began with LLM4Rocq’s rocq-mcp [13] (commit f9219c8),
the only Rocq MCP server we found. It improved on a bare coqc command
but lacked features these large proofs needed, so we forked it. The fork retains
eight upstream tools but replaces the Petanque [5] interactive backend with a
client that drives rocq-lsp [9] directly; Table 1 summarizes the resulting dif-
ferences. In practice the proving agents leaned on four tools: rocq get state
to inspect the goals at a position; rocq query to search the environment for
lemmas and to check types and definitions; rocq step to run a tactic block
speculatively at a position and see the resulting goals without modifying the
file; and rocq compile lsp to check a file incrementally, optionally only up to a
given position, so that an expensive or diverging proof further down never has to
run before a lemma near the top can be confirmed. A completed check can also
be marshaled to a .vof snapshot, rocq-lsp’s serialization of the whole checked
document, so a new session reloads the file’s warm cache in seconds instead of
re-elaborating it from the top.

Extracting and distributing goals. Working inside one giant semax body proof
imposes three costs. Time: a helper lemma added near the top of the file is not
seen by the main proof until the whole prefix between them is re-elaborated, so
every iteration on it pays that full elaboration. Memory: while an agent works
on one subgoal, Rocq still holds all the other goals of the proof in memory. Par-
allelism: a single file is one editing frontier, so several agents cannot work on
different parts of the proof at once. The natural fix would be to factor the proof
into smaller lemmas, but VST is not built for that: its philosophy is that a func-
tion is discharged by a single semax proof, and a goal arising mid-proof (carrying
its full symbolic-execution context) has no convenient standalone statement to
cut it at. To get the effect anyway, our rocq extract tool mechanically cuts a
subgoal out of the live proof: at a chosen point it reads the goal off the running
rocq-lsp session and writes two standalone files next to the source: the goal as a
Definition, its hypotheses lifted into the statement under universal quantifiers
so it closes into a self-contained term, and a Lemma skeleton whose initial proof
state (after re-introducing those binders) is exactly the state at that point. Be-
cause the printed goal is fully elaborated, with every VST notation expanded to
its underlying term, the generated definition can exceed 100,000 lines; agents are
told to treat it as opaque and work only against the Lemma skeleton. The subgoal
is then proved in isolation in its own file, with its own warm cache, by its own
agent, then wired back into the parent with a single eapply. To keep the de-
tached copy honest, the extraction site is annotated with a confirm extraction
marker that hashes the parent goal and detects later divergence. The marker is
a development-only checkpoint: before a body is counted as closed it is replaced
by an ordinary application of the proved lemma, so the final proof depends
on neither the marker nor the extraction plugin, and Rocq checks the lemma
application normally.

Proving agent. A proving subagent is scoped to a single proof file and works on
that file’s open admits. It may edit only its assigned file and add proved helper
lemmas, but may never change a definition, a theorem statement, or a funspec. It
banks verified work behind explicit, provable admits so the file always compiles,
and validated progress is never reverted to restore a clean baseline. A session
ends in one of three ways: the assigned goals are closed; substantial progress is
8       P. Shlyakhtun et al.

banked and a forward-looking hand-off file is updated for the next invocation;
or the goal is found unprovable as stated, in which case the agent works out why
and reports one concrete contract fix: an exact diff, why it is unavoidable, and
why it holds of the C code, without applying it, for human review through the
gate in § 3.1.

Orchestration. An orchestrator agent manages multi-file proving by spawning
proving subagents. It frees a human from scheduling them and maintains a high-
level view of the proof, since no single subagent holds it whole: a typical session
produces a few hundred new tactics before exhausting its context window, so
a large proof is closed over many hand-off-chained sessions. When a subagent
stops, the orchestrator independently rechecks the file with rocq compile lsp
(immediate, thanks to the shared warm cache) and commits validated progress.
When a subagent reports a contract fix, the orchestrator drives it down the
human-reviewed path (§ 3.1): it applies the change in a separate worktree, re-
builds, spawns repair subagents for any proofs that break, and opens a merge
request.

Hooks. Agents occasionally break the intended workflow out of confusion, so we
enforce the key rules mechanically with hooks: scripts the harness runs before or
after a tool call to block it or attach a reminder. Three proved most useful. One
denies reading or editing the ∼100k-line autogenerated goal files (which only
burn context) while leaving the proof body editable. One keeps verification on
the warm rocq-lsp path by blocking coqc and requiring an extra confirmation,
with a reminder of the workflow, before make, so agents do not silently fall back to
the slow, non-incremental check. One addresses a recurring misdiagnosis: agents
sometimes treated a proof-checking timeout as a tooling failure and tried to
route around it, so a reminder clarifies that the timeout is a real problem in the
proof, which agents then fix, typically by replacing an over-broad automation
tactic with a more targeted one.

Guardrails. The Rocq kernel rechecks every accepted proof, and agents may
neither alter trusted funspecs nor introduce admits or axioms into a closed body.
We ran Print Assumptions over every reported body.


3.3   Optimizing Proof-Checking Time

As with human-written formal proofs, a first complete proof is often not the
fastest to check, and at the volume our pipeline generates, proof time matters
as much as proof existence: a tactic that is merely slow in a single hand proof
becomes prohibitive once it runs across hundreds of goals and inside every agent
retry loop. After closing the bodies, we used AI agents to reduce their check-
ing time. Because the scope was the whole project, we relied on mechanical
orchestration rather than a dedicated orchestrator agent: using the beads task
tracker [10] we created one “optimize file X” task per file, and a scheduling script
                   Agent-Driven Verification of liblzma Decoder Components           9

repeatedly spawns an optimizing agent on each unblocked task; the agent pro-
files its file, refactors it, and files follow-up tasks for further ideas, so the swarm
manages itself. Most files optimized this way became at least 30% faster to check
in wall-clock time.
     Guided by the per-sentence profiler, the agents concentrated on a few re-
curring patterns. The most common was reshaping a goal before one of VST’s
heavyweight solvers runs. The grouping of prop conjunctions that entailer!
produces is unstable: adding one conjunct to a loop invariant can fold it into
an unrelated group, and when an existentially quantified stage becomes concrete
entailer! can discharge neighboring conjuncts eagerly. A script written against
one goal shape can therefore fail after a small change. The repair is to inspect
the post-entailer! goal and either script against the observed shape or use
shape-insensitive discharge. Cold-cache time was the other trap: a tactic that is
instantaneous against a warm rocq-lsp cache can exceed a 300-second sentence
timeout cold, which an agent misdiagnoses as a logic failure; the worst offenders
were entailer!/cancel over func ptr-laden sep contexts and full reductions
over large composite environments. The countermeasures are targeted: move a
handful of rewrites or reductions ahead of an entailer! or a cancel to leave
the solver with almost nothing to do; extract a single pure fact with sep apply
instead of a full entailer!; and never simpl or vm compute a whole model
function. Instead, unfold one step and rewrite under control. These changes re-
peatedly reduced individual tactic calls from 40 s or more to under a second
without changing what was proved.
     A second recurring optimization avoided pathological elaboration. Reading
one field of a large nested-record representation drove VST’s solve load rule
evaluation tactic, which computes the loaded value, to cbv-reduce the projec-
tion through the entire record type on every forward, costing 40 s or more per
field access. An agent rebound this tactic with Ltac’s ::= mechanism, without
modifying VST or the specification: for each affected field read the proof estab-
lishes, once, a JMeq equality relating the projection to the loaded value, and the
redefined tactic closes its goal from such an equality when one is present and
otherwise delegates to the original tactic. Each affected forward then resolves
in milliseconds instead of tens of seconds.


4    A Reviewed Coupling Invariant

We illustrate the reviewed agent–human interaction through one invariant repair
in the LZMA2 framing decoder proof. The decoder processes a stream as a
sequence of compressed or uncompressed chunks and may return when an input
or output buffer is exhausted, then resume the same chunk on a later call. Its
sequence field records the current phase: Control reads the next chunk’s control
byte, Uncompressed1/2 and Compressed0/1 parse its size fields, Properties
configures the embedded LZMA1 decoder, Lzma decodes a compressed payload,
and Copy copies an uncompressed one. During a partially consumed header,
next sequence records the phase that follows it.
10      P. Shlyakhtun et al.

    The VST proof establishes a loop invariant before the first iteration and re-
establishes it after every continuation. The invariant describes the states that
may occur at the loop head and relates the outer LZMA2 phase to the embedded
LZMA1 child’s initialization stage. Our functional model records that stage with
four constructors: NoChild before installation, Raw after installation, Sized after
assigning its output size, and DecodeReady after reset makes it ready to decode.
Treating the outer phase and child stage independently admits combinations
that no execution of the C program can reach. The coupling clauses exclude
those combinations and supply facts needed to verify the next branch or child-
decoder call. The reviewed loop invariant asserts the following constraints; each
is stated with the unreachable state it excludes.
 (a) A Raw child is never at Properties or Lzma; once properties are available,
      its next header phase is Properties. This excludes using a merely allocated
      child as though its probability state had already been initialized.
 (b) A Sized child is never in the Lzma or Copy sequence. This excludes entering
      decoding or an uncompressed copy while the child is between its output-size
      assignment and the reset that makes it ready.
 (c) At Control, any child that is not DecodeReady still requires properties.
      This excludes a control state that advertises completed property setup while
      retaining an incompletely initialized child.
 (d) During normal header progression, next sequence is coupled to both the
      current header and the child stage: Copy follows only a compressed-size
      header with a non-Sized child; Properties follows an uncompressed header
      or a sufficiently initialized child; and Lzma requires DecodeReady. This ex-
      cludes stale pairings such as Sized/Copy. The clause is conditioned on prop-
      erties being available, so the immediate error return that deliberately leaves
      next sequence stale remains representable.

A reported invariant gap. In the Compressed1 branch, a proving agent reached
an obligation that required next sequence <> Copy when the child was Sized.
The current invariant did not imply it: its Copy alternative carried no stage
constraint and therefore admitted the Sized/Copy state. Following the frozen-
specification rule, the agent stopped and reported (i) why the goal was not
derivable, (ii) why the combination was nevertheless unreachable in the C code,
and (iii) a candidate strengthening that it did not apply. The source argument
was that Sized arises only on the compressed-chunk path, which sets the next
phase to Lzma or Properties; the uncompressed-copy path that sets Copy does
not resize the child, which remains DecodeReady.
    The specification owner reviewed that reachability argument and approved
the strengthened Copy clause in item (d). The change was not local: every pro-
ducer of the invariant acquired a new obligation. In the next session, agents
re-established the clause at nine producer sites and at its consumers; a final pass
threaded the same fact through the uncompressed-copy branches and closed
the framing body theorem. A condensed version of the report and the accepted
clause appear in Appendix B. This episode follows the review path in Figure 2.
We triage a stuck goal as proof work or a possible specification gap. Here the

5     Proof Engineering for Production C and VST

The C-to-proof path in Figure 2 required three engineering steps: recovering
build-configured source, testing the functional model against executions, and
regularizing unsupported C constructs.


5.1    From Build-Configured C to Clight

The pipeline begins with the project’s build configuration. Production C is mean-
ingful only under the exact macros, include paths, and preprocessor flags its build
system selects. Macro expansion itself is not the problem: clightgen invokes a
preprocessor, and a compiler’s -E option can expose the expanded source. Neither
mechanism discovers which definitions and include paths CMake assigns to each
translation unit. Our immerse command runs CMake with a compiler wrapper.
During configuration, CMake compiles small feature-probe programs to detect
compiler and platform capabilities. The wrapper forwards these probes to ccomp,
CompCert’s compiler driver, allowing configuration to complete; during the gen-
erated build, it replaces each compilation with clightgen -normalize, passing
that command’s -D and -I options and writing the resulting Rocq file into a mir-
rored output tree. Adding a source file to the intercepted build therefore brings
it into Clight generation without a separately maintained list of definitions and
include paths.


5.2    Grounding the Model in Execution

Execution grounding compares the functional model with concrete runs of the
configured C program before the more expensive body proof. This matters for
a resumable decoder: matching final output may not reveal an incorrect inter-
mediate range-coder or dictionary state that affects a later call. Human review
still determines model and contract meaning; the comparison provides comple-
mentary evidence of discrepancies.
     We use LLDB’s scripting API to place breakpoints at entry to and return
from lzma decode and to inspect the buffer and struct states described by our
data at assertions.7 A Python handler reads the live buffers and structs and uses
a mapping from their C layouts to our Rocq representations to lift each call’s
inputs and observed outcome. Configurable buffer sizes force both complete calls
and suspension followed by resumption. The snapshots pass through a JSONL
trace into a generated Rocq module; a harness runs the functional model on the

    Clight generation. We assigned explicit tags to anonymous structure definitions

    ated composite types stable names without changing their layout or run-time
    behavior. We also added a translation-only harness that references the static-
    inline dictionary operations so that clightgen emits their bodies; the harness
    is not called by the decoder and is outside the verified call graph.

   unstructured switch [2, p. 9]. The main loop of lzma decode is built around
   Duff’s device, so we instead replaced that control flow with explicit structured

Verifying real C with VST. VST provides a foundational separation logic for C
whose soundness is tied to the CompCert semantics, while VST-Floyd supplies
the forward symbolic execution used in our body proofs [4,7]. It has previously

been applied to cryptographic C, including OpenSSL HMAC [6] and SHA-256 [3].
We apply the same foundation to stateful, resumable decoder machinery, placing
adaptive proof search in external agents and keeping model and contract changes
under review.

Agentic LLM experience reports for mechanized proof. Three recent reports
apply AI agents to substantial Rocq developments. Paraskevopoulou [16] uses

mantics.

B     An Agent-Reported Specification Gap

The report-only rule above produces a characteristic artifact. The agent must
explain why the goal is not derivable from the current invariant, justify why the
desired fact nonetheless holds of the C code, and leave a concrete fix for the
owner to apply. The example below is condensed from the internal handoff log
of the framing decoder body proof; it concerns the coupling invariant between
the LZMA2 sequence machine and the embedded LZMA1 child decoder’s ini-
tialization stage (§ 4). The proof was blocked in the Compressed1 case: with the
child in stage Lzma1Sized and next sequence = Copy, the output state’s stage
validity requires Copy <> Copy, which is unprovable. The agent’s report, lightly
edited for notation:

(a) Why it is not derivable. The coupling hypothesis with stage = Lzma1Sized
    only bounds the next sequence to {Copy, Properties}: the Lzma disjunct is
    excluded by discrimination, but the Copy disjunct of the coupling carries no
    stage constraint. No other loop-invariant conjunct relates next sequence
    to the child stage, so the invariant genuinely admits the state stage =
    Lzma1Sized ∧ next sequence = Copy.
(b) Why it is true of the C code. A Sized child arises only from the compressed-
    chunk header path through lzma decoder uncompressed. Control bytes at
    least 0x80 set the next sequence to Lzma or Properties. Only control values
    1 and 2 select Copy; that uncompressed path does not touch the child, which
    remains DecodeReady from the previous chunk. Hence a Lzma1Sized stage
    rules out a Copy next sequence in every reachable state, but the invariant
    does not capture this fact.
(c) The concrete fix (marked “do NOT apply without owner sign-off; spec is
    frozen”): strengthen the coupling’s Copy disjunct to carry a stage constraint,
    mirroring the Lzma disjunct, with the caveat (worked out in the report) that
    this is a multi-point strengthening (it obligates every producer of the post-
    condition), not a one-line edit.

C    Separation Lenses for Struct Footprints
During development we used the paper-local term separation lens for a repre-
sentation technique that regularized proofs over large structs. VST otherwise
represents the decoder’s 29-field struct as one deeply nested spatial assertion,
while most operations access only one or two fields. A separation lens consists
of a per-field spatial predicate, a whole-struct predicate parameterized by the
fields temporarily removed from it, and focus/unfocus lemmas:
Lemma rep_focus f absent cs p:
  set_mem f absent = false ->
  lzma1_decoder_rep absent cs p
  |-- field_rep cs p f * lzma1_decoder_rep (f :: absent) cs p.

Lemma rep_unfocus f absent cs p:
  set_mem f absent = false ->
  field_rep cs p f * lzma1_decoder_rep (f :: absent) cs p
  |-- lzma1_decoder_rep absent cs p.
    Here f selects a field, cs is the logical decoder state, p is the C struct
pointer, and absent records fields already separated from the whole-struct pred-
icate. rep focus extracts one field’s predicate while preserving the remainder;
rep unfocus reverses that operation. A proof can therefore perform a local op-
eration while keeping all other fields framed as a single predicate. This made
evolving proof goals more regular and sped up intermediate versions of the de-
velopment. The final proof does not depend on these lenses; we include them
because they were used during development.
