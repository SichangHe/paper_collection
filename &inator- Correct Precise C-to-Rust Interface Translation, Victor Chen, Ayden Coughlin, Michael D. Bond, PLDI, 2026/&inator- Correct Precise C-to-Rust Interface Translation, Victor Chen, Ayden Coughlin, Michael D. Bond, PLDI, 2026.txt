Automatically translating system software from C to Rust is an appealing but challenging problem, as it
requires whole-program reasoning to satisfy Rust’s ownership and borrowing discipline. A key enabling step
in whole-program translation is interface translation, which produces Rust declarations for the C program’s
top-level declarations (i.e., structs and function signatures), enabling modular and incremental code translation.
This paper introduces correct, precise C-to-Rust interface translation, called &inator. &inator employs a
novel constraint-based formulation of semantic equivalence and type correctness including borrow-checking
rules to produce a Rust interface that is correct (i.e., the interface admits a semantics-preserving implementation
in safe Rust) and precise (i.e., it uses the simplest, least costly types). Our results show &inator produces
correct, precise Rust interfaces for real C programs, but support for certain C features and scaling to large
programs are challenges left for future work. This work advances the state of the art by being the first correct,
precise approach to C-to-Rust interface translation.

Introduction

The C programming language’s lack of memory safety has led to countless bugs and vulnerabilities,
costing billions of dollars annually and imperiling human well-being and security [13]. There
is growing support among researchers, practitioners, and government for migrating safety- and
security-critical system software from C to memory-safe languages, with (the safe subset of) Rust
as the exemplar, owing to its combination of safety and bare-metal performance [2, 20, 28].
However, translating the world’s system software from C to Rust requires more than localized
syntactic and semantic conversion [15, 25]. The central obstacle is Rust’s strict ownership and
borrowing discipline, which ensures safety but is tough to adhere to. Large language models (LLMs)
are good at converting C code into idiomatic Rust code, but not code that satisfies Rust’s ownership
and borrowing rules while also ensuring semantic equivalence [11, 21, 29, 31]—a challenge that
requires deep, program-wide reasoning. Mechanical (non-LLM) C-to-Rust translators emit large
amounts of unsafe Rust code [5, 6, 9, 16, 30] or cannot handle common aliasing patterns [8].

Key problem and motivation. A key enabling step of C-to-Rust translation is interface translation:
choosing Rust types for a C program’s top-level declarations (e.g., struct fields, function parameters,
and return values). While not technically required as an explicit step, interface translation is the
foundation for modular code translation: Once correct interfaces are chosen, function bodies can
be translated one at time, with confidence that the pieces will fit together. By contrast, a mistaken
type choice in the interface cascades into widespread translation failures [11, 29]. Fig. 1 shows how
interface translation fits into the C-to-Rust translation workflow. Furthermore, interface translation
is compatible with a translation paradigm that preserves a direct mapping of functions and structs
between the C and Rust programs, making it compatible with incremental translation (i.e., some
functions in idiomatic Rust and others still in C or unidiomatic or unsafe Rust).
Prior work recognizes the importance of interface translation. Tymcrat performs LLM-based
interface translation, with the authors stating that “[t]his step is crucial because directly requesting
the LLM to translate the function may not migrate types correctly” [11]. The authors of Fluorine,
a Go-to-Rust translator, similarly report that a mistaken interface type cascades into widespread
translation failures [29]. CRUST-Bench, a C-to-Rust translation benchmark suite, distributes handtranslated interfaces so that code translators can even be evaluated [12].
Interface translation is challenging. Interface translation is hard for both humans and machines. The
difficulty lies in simultaneously satisfying Rust’s ownership and borrowing rules and preserving
semantic equivalence with the C program. This requires whole-program reasoning. A successful
translation must have the following properties:
• Correct: The chosen types admit a safe Rust implementation that preserves the semantics of
the original program.
• Precise: Among correct types, the types should be the least costly (according to some cost
function).
For example, a C function parameter of type T* might plausibly map to Rust types &T, T, &[T],
Vec<T>, Box<T>, Rc<RefCell<T>>, and others. Which are correct, and which is best?
Consider the C program in Fig. 2(a) and a corresponding Rust interface in Fig. 2(b). The Rust
interface consists of struct and function declarations. The figure shows semantics-preserving
function bodies (in gray) to demonstrate that the interface is viable. Even in this small example,
subtle challenges arise. For example, the most precise correct type for replace’s parameter dst is
&mut i32. The types &i32 and i32 are incorrect, while Rc<RefCell<i32>> is correct but imprecise.
As another example, the Node::next field must be an owning type instead of a borrowed reference
(e.g., Node or Rc<Node> instead of &Node) because a pointer escapes from push into a Node. The function
replace_first must take an immutable reference to avoid borrowing conflicts in main even though
it mutates its list parameter, which forces Node::next to be interior mutable (i.e., to use RefCell).
Making such determinations requires a global understanding of the C program’s semantics and
Rust’s ownership and borrowing rules. For example, the analysis must recognize that list.next.
as_ref().unwrap() and *list.next.take() are available to transform Rust values in a way that
obeys Rust’s borrowing rules and preserves the semantics of the C program.

Prior work has not solved C-to-Rust interface translation (§ 2). Tymcrat attempts LLM-based
interface translation but frequently fails to produce correct, precise interfaces [11]. Scylla’s mechanical translation approach includes interface translation implicitly [8], but it cannot handle
aliasing, lacks dynamic borrowing support, and fails to choose precise types because it forgoes
precise global reasoning. CRUST-Bench allows translation approaches to sidestep the difficulty
entirely, by distributing hand-translated interfaces [12].
Our approach. This paper takes the first steps in developing interface translation that is correct and
precise. The paper’s novel interface translation approach, called &inator,1 encodes type correctness
and semantic equivalence as logical constraints. Key insights include (1) a novel method for mapping
“type fragments” between C and Rust to make the type space bounded and solvable and (2) a novel
formulation of Rust’s ownership and borrowing rules, including support for legal transformations
between Rust types that enable precise translation.

Conceptually, &inator’s approach can be viewed as inferring an ownership and borrowing
discipline for C code and expressing it using Rust’s type system. This perspective connects our
work to prior efforts to infer safety-oriented types for C [7, 10, 17, 19] (§2).
&inator currently has four main limitations. First, &inator’s interface translation is based on a
strict interpretation of the aliasing in the input C program. As a result, the translated interface may
be less precise than what could be produced by considering semantics-preserving reordering that
can impact aliasing. Second, &inator currently cannot handle certain C features, including function
pointers and polymorphic pointers. Third, for some Rust types, &inator infers a set of possible
types rather than an exact type. Fourth, &inator’s running time currently scales superlinearly with
program size, and it takes several hours to solve constraints for C programs with a few thousand
lines of code. Addressing these limitations is left for future work.
We implemented &inator to take LLVM IR as input and generate SMT constraints solved by
Z3. We evaluated &inator using three metrics: correctness and precision of translated interfaces
and run-time performance of interface translation. The evaluation uses several programs from
CRUST-Bench [12]. The results show that &inator chooses correct, precise interface types nearly
universally. Constraint solving takes several hours for C programs with a few thousand lines of
code.
This paper contributes a novel formulation of cross-language type inference under a safety
discipline, demonstrated empirically on real C programs. It shows, for the first time, the potential
for correct, precise C-to-Rust interface translation.

Background and Related Work

No prior work solves the interface translation problem. Table 1 compares C-to-Rust interface
translation approaches with &inator. Note that several of the approaches perform interface
translation implicitly as part of whole-program translation, rather than as an explicit step. An
approach supports aliasing if it handles C programs with arbitrary aliasing. An approach is modular
if it does not require whole-program analysis. &inator requires whole-program analysis, but its
analysis results enable modular code translation.
Mechanical translation to safe Rust. Fromherz and Protzenko introduce Scylla, a mechanical approach for whole-program C-to-Rust translation [8]. However, Scylla does not support aliasing in
general nor dynamic borrowing, making it infeasible to refactor some C programs to be eligible for
translation. Furthermore, Scylla fails to choose precise types because it forgoes global reasoning.
Mechanical translation to unsafe Rust. Several approaches translate C to a mix of safe and unsafe
Rust, which we consider incorrect solutions to the problem of producing safe Rust interfaces
(Table 1).

C2Rust is a mature project that mechanically translates C programs to Rust [9]. However, most of
the generated code is unsafe (i.e., uses operations marked unsafe) and may violate memory safety,
particularly dereferences of raw pointers.
Several approaches attempt to convert the output of C2Rust to use less unsafe code, with limited
success. Laertes uses heavyweight pointer analysis to make C2Rust’s output safer, but it cannot
change many raw pointers to safe types [5, 6].
In a similar spirit, Crown rewrites Rust code produced by C2Rust to use fewer raw pointers [30].
Crown avoids Laertes’s heavyweight pointer analysis, instead encoding ownership rules as SMT
constraints that encode a conservative version of Rust’s ownership and borrowing rules. While
Crown bears some resemblance to &inator, there are significant differences. Crown’s analysis is
mostly intra-function: It does not modify function signatures to eliminate raw pointers and unsafe
types, except for output parameters. (Crown however uses global constraints to choose new types
for struct fields.) In contrast, &inator translates function signatures, using global constraints
that capture dependencies across function call boundaries and between multiple variables’ types.
Furthermore, Crown determines only whether types should be owning, while &inator determines
complete type information, enabling interface translation. Finally, Crown fails to remove many
raw pointers, while &inator removes raw pointers, even in the presence of aliasing.
CRustS performs template-based translation on C2Rust-translated code to use less unsafe code,
but it primarily encapsulates unsafe code without eliminating it [16].
LLM-based translation. Tymcrat performs LLM-based interface translation as its first step, generating
multiple candidate interfaces and trying each of them in LLM-based code translation [11]. There are
no guarantees about the correctness or precision of the interfaces, which are often incorrect [11],
and code translation treats the interfaces as a hint rather than a mandate.
In addition to Tymcrat [11], recent work uses LLMs to translate C to Rust, but generally fails to
produce compilable, correct translations for nontrivial inputs. LLM-based translation is not modular,
and one can expect its correctness and precision to degrade with increasing program size and
complexity due to LLM reasoning capacity limits. &inator is not modular, but its correctness and
precision do not degrade with increasing program size and complexity, and it can enable modular
LLM-based code translation.
C2SaferRust uses LLMs to transform (mechanically translated) unsafe Rust to more safe Rust [21],
but it still leaves much code unsafe. SACTOR likewise translates unsafe Rust to safe Rust, using an
LLM guided by hints from static program analysis [31]. Unlike &inator’s constraint generation–
based approach, SACTOR’s static information is insufficient for correctly translating types, but
instead is intended to help the LLM choose better types more often. Fluorine shows the utility
of “feature mapping” to help LLMs translate across languages and “type compatibility” to ensure
compatibility of types across languages [29]. However, neither technique takes into account the
semantics of ownership and borrowing in Rust.
Outside the context of translation, Mündler et al. constrain LLM token generation to produce
type-correct code [18], but their approach does not support ownership or borrowing.
Type inference. Rust interface translation can be viewed as a form of global type inference. Edwards
and Li explore global interface inference in the context of translation [4], and other approaches
perform type inference on languages with memory safety features [7, 10, 17, 19]. None of these
approaches infer types for languages with statically enforced ownership and borrowing.

Guarantees and Requirements

&inator’s inferred interface is correct if there exists a safe Rust translation using the interface that
preserves the C program’s behavior, except for potential dynamic borrowing conflicts and memory
leaks mentioned below. For a C program without undefined behavior, &inator infers a correct
interface (modulo the limitations below). For a C program with undefined behavior, &inator still
infers an interface, which we expect in practice to admit a safe Rust translation with the intended
behavior of the C program—a translation that likely panics in cases where the C program would
dereference a NULL pointer or read past the end of a buffer, for example.
&inator always infers a correct interface (i.e., its constraints are always satisfiable) because it is
possible to implement any C interface in safe Rust by using Rc<RefCell<T>> for every pointer.
&inator requires whole-program analysis to perform correct and precise interface translation,
impacting its scalability. In addition, the entire C program needs to be available as input to &inator.
For an incomplete program such as a library, &inator requires a client test suite that uses the
library. The same requirement applies to other translation approaches.
3.2

Limitations

&inator infers types based on a strict interpretation of aliasing in the input C program. As a result,
it cannot infer an interface that relies on code reordering that impacts aliasing.
&inator may not guarantee that there exists a panic-free safe Rust translation that uses the inferred interface and preserves the C program’s behavior—this is because of the possibility of dynamic
borrowing conflicts caused by conflicting RefCell::borrow and RefCell::borrow_mut calls.2 We are
most concerned about cases in which &inator chooses an interface variable type of std::cell::Ref
or std::cell::RefMut (the return types of RefCell::borrow and RefCell::borrow_mut, respectively).
This could lead to a function that takes a RefMut as input and yet requires access to the same
RefCell, for example. This concern could be addressed by disallowing Ref and RefMut as interface
types. Future work should determine the extent of this issue and how to address it.
&inator does not differentiate between some types, which we discuss in §5. &inator cannot
guarantee that the inferred interface admits a memory leak free safe Rust translation, even when the
C program is memory leak free, since the interface may require that any safe Rust implementation
uses Rc cycles. &inator does not currently support multi-threaded programs or libraries.
&inator currently provides partial or no support for certain C program features: function
pointers, polymorphic pointers, union types, variadic functions, and the ternary operator. Supported
type casts include coercions on integral types and void pointers cast to a single non-void pointer
type. Unsupported type casts include void pointers cast to more than one other pointer type and
struct pointers cast to pointers to the struct’s first field. §11.1 provides details on these limitations.
3.3

How &inator Works

&inator performs the following steps as shown in Fig. 3:
(1) Convert the C program to &inator’s source language (§4).
(2) Generate SMT constraints on the inferred Rust types that ensure type correctness, semantic
equivalence, and precision (§6–§10).
(3) Run an off-the-shelf SMT solver to solve the constraints, yielding correct, precise Rust types.

IR [14], but it represents more precise types than LLVM IR, called source types; is explicit about
when variables are dropped; and tags parts of its syntax with type labels.

Overview of Constraints Generated by &inator

&inator generates SMT constraints on inferred Rust types that enforce semantic equivalence with
the input source program and adherence to Rust’s type-checking rules. It generates constraints to:
(§7) Ensure the inferred types are consistent with the source program and self-consistent. The
constraints encode standard Rust typing rules—e.g., structs are well-formed, expressions are
well-typed, and only mutable-typed pointers can be used mutably—according to the rules
described in the Rust Reference [26] and the Rust Standard Library API [27].
(§8) Ensure the inferred types account for Rust’s copy and move semantics, which differ from
the source language’s (C-like) copy semantics, and affect aliasing relationships and when
memory locations are invalidated.
(§9) Ensure Rust’s borrowing-checking rules are satisfied, based on the operational description in
Rust’s non-lexical lifetimes RFC [22] and compiler development guide [24].
(§10) Ensure the inferred Rust types are precise. These constraints are based on a principled model
of the relative complexity and cost of Rust pointer types.
The main paper describes the generated constraints in an intuitive, example-driven way. The formal
details are in appendices, with §A introducing common notation and definitions.

Type Consistency Constraints

Here, we describe constraints &inator generates to ensure that (1) the inferred Rust types are
consistent with the source program’s types and (2) a Rust translation using these types would
adhere to Rust’s type-checking rules, excluding borrow-checking rules (which are handled in §9).
The formal constraints generated by &inator are presented in §B.
7.1

Type Parity

The first set of constraints &inator generates ensures that the inferred Rust types are consistent
with the source types in the source program. &inator emits constraints that, for each type label ℓ
in the program, the RTypeFrag assigned to ℓ matches the STypeFrag assigned to ℓ.
The general rule is that each primitive source type fragment matches the corresponding primitive
Rust type fragment (e.g., i32 matches i32), struct source type fragments match corresponding struct
Rust type fragments with any lifetimes (i.e., struct(𝑠) matches struct(𝑠, _)), and the pointer
source type fragment matches any pointer Rust type fragment (i.e., ptr matches ghost_ , Box_ Rc_ ,
shared_ (_), mut_ (_)). The challenge in choosing correct, precise Rust types thus lies in choosing a
pointer Rust type fragment for each pointer source type fragment.
For example, in Fig. 5 and Fig. 7, Node::data has source type ⟨[ptr] 0, [i32] 1 ⟩ and Rust type
⟨[ghost] 0, [i32] 1 ⟩. This Rust type satisfies the type parity constraints based on the source type
since the source type fragment [ptr] 0 matches the Rust type fragment [ghost] 0 , and likewise for
the source type fragment [i32] 1 and Rust type fragment [i32] 1 .
7.2

Struct Consistency

&inator generates constraints to ensure that struct definitions are well-formed; that is, each
lifetime parameter in the Rust type of a struct field appears in the list of parameters declared in
the Rust struct definition. For example, in Fig. 7, the Rust type fragments of fields Node::data and
Node::next must only be parameterized on lifetime variables declared in the definition of the struct
Node. The inferred Rust types in Fig. 7 satisfy this constraint because none of the type fragments of
Node::data and Node::next are parameterized on any lifetime variables, and there are no lifetime
variables declared in the definition of struct Node. If any of these type fragments contained a lifetime
variable, the constraints would not be satisfied.
7.3

Recursive Struct Definitions

Rust requires recursive structs to be defined with finite size [26]. Consider Fig. 7, where the Rust
type of Node::next is ⟨[ghost] 2, [RcCell ] 3, [struct(Node, ⟨⟩)] 4 ⟩. Despite being recursively defined,
struct Node is finitely sized due to the indirection in the Rust type of Node::next.
Now, if the Rust type of Node::next were ⟨[ghost] 2, [ghost] 3, [struct(Node, ⟨⟩)] 4 ⟩, which has
no indirection, then the struct Node has infinite size, and cannot compile.
&inator emits constraints to ensure structs are defined with finite size by introducing the notion
of an integer rank for each struct. &inator generates constraints requiring that a struct’s rank be
greater than the rank of any struct it contains directly as a field (i.e., without indirection through
pointers). Inferring ⟨[ghost] 2, [ghost] 3, [struct(Node, ⟨⟩)] 4 ⟩ as the Rust type of Node::next requires StructRank( Node) > StructRank( Node), which is unsatisfiable.

Type Equivalence

&inator generates constraints that for each assignment,4 the Rust types of the expressions on either
side of the assignment are equal, except for lifetime variables. This requirement matches the Rust
type checker’s rules. For example, if x is a variable of type i32, then let p: &'a i32 = &'b x;
is allowed by the Rust type checker,5 even though p and &'b x have different lifetimes. But,
let p: &'a i8 = &'b x; is not allowed because the types &'a i8 and &'b i32 differ by more than
their lifetimes.

7.7

Immutability Preservation

In Rust, it is not permissible to obtain a mutable reference to data behind an immutable pointer,
except when the referent is interior mutable. For example, if 𝑝 is a pointer with (immutable) type
&Node or Rc<Node>, then it is not possible to get a &mut reference into the Node::data field of *𝑝 ,
so &inator does not allow any rvalue expression with path &*(*𝑝).data to be a mut reference.
&inator thus generates constraints that an rvalue expression cannot have a mutable pointer type
if it takes a pointer to data behind an immutable pointer to a non-interior mutable type.
7.8

Mutability

In Rust, only certain pointer types allow their referent to be mutated: the singly-owning Box<T>
pointer and the mutable reference &mut T. It is also possible to mutate a referent whose type provides
interior mutability. For example, the referent of a &Cell<T> or Rc<Cell<T>> can be mutated even
though shared references and Rcs are immutable pointers.
In the source language, the only instruction that mutates the referent of a pointer is *𝑣 = [𝑒] ℓ ;.
So, for each *𝑣 = [𝑒] ℓ ; instruction, &inator generates a constraint that the outermost Rust type
fragment of the variable 𝑣 allows mutation of its referent.
7.9

Ownership

In Rust, all allocated objects must have an owner. So, &inator generates constraints that all
instructions that allocate memory on the stack or heap and yield a pointer to the new allocation
(e.g., 𝜏® 𝑣 = alloca(𝑐);) must yield an owning pointer (i.e., ghost_ , Box_ , or Rc_ ).
7.10

External Functions

&inator generates constraints to ensure that the inferred types are consistent with the signatures of
external functions whose bodies are not available—most importantly, for mutable pointer arguments
to libc functions. For example, &inator generates a constraint that the outermost type fragment of
dst in the function declaration memcpy(void *dst, void *src, size_t n) is mut_ (_). We derived
these constraints manually for all libc functions called from our evaluated programs.

Semantic Preservation Constraints

This section describes at a high level the constraints that &inator generates to ensure that a Rust
translation using its inferred types is semantically equivalent to the source program. The formal
constraints generated by &inator are in §C.
To preserve the semantics of the source program, it suffices to ensure that using &inator’s
inferred types, there is a Rust translation of each source language instruction that does not illegally
invalidate any paths. In the source language, using an expression as an rvalue never invalidates

be Copy are (1) the pointer types and (2) struct and unknown types accessed behind pointer types,
&inator only needs to constrain pointer type fragments to preserve the semantics of the source

8.1

Referent Preservation

In Rust, it is illegal to invalidate a path derived from a borrowed reference. For example, if 𝑝 is
a pointer with type &mut Box<T>, then the statement let 𝑞 = *𝑝; invalidates the path *𝑝 , but the
Rust compiler prohibits this because 𝑝 is a mutable reference. Although it is sometimes possible
to invalidate a path derived from an Rc<T> pointer via Rc::into_inner, &inator cannot statically
guarantee that doing so will not introduce panics, so &inator considers it illegal to invalidate
any path derived from an Rc pointer. So, invalidating a path derived from a pointer may be legal
only when the pointer is singly-owning, i.e., one that corresponds to ghost_ or Box_ . Therefore,
for pointer-typed [*𝑣 ] ℓ and [&*(*𝑣).𝑓 ] ℓ rvalue expressions, &inator generates constraints that
ensure the path of the rvalue expression is not invalidated unless 𝑣 is a singly-owning pointer.
8.2

The constraints presented in this section prevent pointer transformations from invalidating live
paths. This is sufficient to prevent all reads of invalid paths. To achieve this, we identify a subset
of pointer transformations as nondestructive transformations. Nondestructive transformations are
pointer transformations that do not invalidate any path in their operand, and are shown in Fig. 8
by solid edges. &inator generates constraints that, for each pointer-typed non-nested rvalue
expression, the type of the rvalue expression nondestructively transforms from the type of its path,
unless the pointer-typed variable in the rvalue expression dies.
For example, consider line 15 in Fig. 7, where the variable list remains live because the rvalue
expression [list] 44 is used later in line 19. One of &inator’s nondestructive pointer transformationation constraints is that the type of list is nondestructively transformable to the type of

The borrow-checking rules solve for the lifetime of each lifetime inference variable. A lifetime is a
set of program points (Point𝑀 ), and we say the lifetime inference variable 𝜌 ∈ LifeVar is live at
program point 𝑝 ∈ Point𝑀 if 𝑝 is in the lifetime of 𝜌. Intuitively, the lifetime of a 𝜌 ∈ LifeVar is
the set of program points where a reference or struct containing 𝜌 in its type is live or aliased.
Using the solved-for lifetimes, the borrow-checking rules check that no use of a path conflicts
with the set of in-scope loans at the program point immediately preceding it. A loan (𝜌, 𝑎) ∈ Loan
is a pair comprised of a lifetime inference variable 𝜌 ∈ LifeVar and a path 𝑎 ∈ Path. We say the
loan (𝜌, 𝑎) is in scope at the program point 𝑝 ∈ Point𝑀 if 𝑎 is borrowed by a reference with lifetime
inference variable 𝜌 and 𝜌 is live at 𝑝. A use of a path conflicts with an in-scope loan if the use
accesses a mutably borrowed path, writes to a borrowed path, or invalidates a borrowed path. A
drop of a variable also conflicts with in-scope loans of paths involving that variable, if that variable
is not a reference.
&inator generates constraints that (1) compute the in-scope loans at each program point (§9.1
and §9.2) and (2) disallow borrowing conflicts (§9.3). §D presents the constraints in detail.
9.1

Lifetimes

&inator generates constraints to infer (1) the lifetime of each lifetime inference variable based
on liveness, subtyping, and reborrowing, following the NLL RFC [22], and (2) the lifetime of each
function lifetime parameter, following the Rust Compiler Development Guide [24].
Liveness. A lifetime inference variable 𝜌 ∈ LifeVar is live at every program point where a variable
with a type that mentions 𝜌 is live. For example, in Fig. 7, the variable next is live at (17)in,7 and
the lifetime inference variable 'i appears in the type of next, so &inator generates a constraint
that ensures 'i is live at (17)in .8
Subtyping. The borrow-checking rules infer that for an assignment 𝑑 = 𝑠 , the type of 𝑠 must be
a subtype of the type of 𝑑. Each lifetime inference variable in 𝑠 must outlive the corresponding
lifetime inference variable in 𝑑, and depending on the types of 𝑠 and 𝑑, some outlives relationships
in the opposite direction must hold.
According to the Rust Reference [26], the shared reference type &'a T is covariant in both 'a
and T; that is, the Rust type &'a T is a subtype of &'b U if 'a outlives 'b and T is a subtype of U.
However, the mutable reference type &'a mut T is covariant in 'a but invariant in T; that is, the
Rust type &'a mut T is a subtype of &'b mut U if 'a outlives 'b and T is exactly U, including lifetimes.
Similarly, Cell<T> is invariant in T.

In-Scope Loans

&inator generates constraints that, in effect, compute the in-scope loans at every program point
using data-flow analysis, based on the data-flow analysis described in the NLL RFC [22]. Data-flow
facts are the set of in-scope loans, and control-flow merges take the union of facts because the
analysis is a may analysis.
Let Loans : Point𝑀 → P (Loan) be a function that gives the data-flow facts at each program
point. The transfer function at an instruction at line 𝐿 ∈ InstrLab𝑀 is defined as follows using one
gen set, genborrow (𝐿) ⊆ Loan, and two kill sets, killlifetime (𝐿) ⊆ LifeVar and killassign (𝐿) ⊆ Path.
Loans((𝐿)out ) = ((Loans((𝐿)in ) \ killlifetime (𝐿) × Path) ∪ genborrow (𝐿)) \ LifeVar × killassign (𝐿)
The gen and kill sets are defined at each label 𝐿 ∈ InstrLab𝑀 as follows.
(1) For each 𝜌 ∈ LifeVar, 𝜌 ∈ killlifetime (𝐿) if and only if 𝜌 is dead at (𝐿)out .
(2) (𝜌, 𝑎) ∈ genborrow (𝐿) if and only if an rvalue expression that borrows the path 𝑎 appears in
the instruction at 𝐿 and 𝜌 is live at (𝐿)out .
(3) killassign (𝐿) = {𝑣, *𝑣 } if the instruction at 𝐿 is *𝑣 = [𝑒] ℓ ;. Otherwise, killassign (𝐿) = ∅.

(2) *𝑣 is an owning pointer and 𝑎 = **𝑣 .

because n in push is an owning pointer, &inator generates a constraint that ensures that there are

the push function into list, if Node::next were a borrowed reference, then a loan of *n would be in
scope when n is dropped, so this constraint forces Node::next to be an owning pointer.

Precision

The constraints presented so far ensure that Rust types are correct, but the types may not be precise
(i.e., simplest and least permissive), which is desirable for minimizing run time and memory usage,
as well as for avoiding run-time borrowing panics in translated function bodies using the inferred
interface types (§3.2). To achieve precise types, &inator minimizes the following objectives in
descending order of priority: (1) the number of Cell qualifiers, (2) the sum of the transformation
cost of each pointer Rust type fragment, (3) the sum of the run-time cost of each pointer Rust type
fragment, and (4) the number of array qualifiers.12 For these objectives, &inator only considers
type fragments that appear in interfaces.
The transformation cost of a pointer Rust type fragment roughly corresponds to the number of
type fragments to or from which it is transformable, depending on its location. The outermost type
fragments of struct fields and a global variables are singled out because they correspond to extra
indirection introduced by compilation to LLVM IR or conversion to the source language, and are
likely redundant. For these type fragments, &inator considers owning pointer type fragments
(ghost_ , Box_ , Rc_ ) to be less costly than borrowed pointer type fragments since owning pointer
11 These paths correspond to the paths of relevant loans for “shallow” accesses of a path in the NLL RFC [22].
12 In (1), Cell qualifiers refer to both Cell and [Cell]. In (4), array qualifiers refer to both [] and [Cell].

type fragments are transformable to more type fragments than borrowed pointer type fragments.
This cost function encourages redundant indirection to be removed via ghost_ type fragments. For
other Rust type fragments, &inator considers borrowed pointers (shared_ (_), followed by mut_ (_))
to be less costly than owning pointer type fragments since borrowed pointers are transformable
from more type fragments than owning pointer type fragments. This cost function encourages
&inator to choose the least permissive types whenever possible, e.g., using a shared_ (_) instead
of an Rc_ .
The run-time cost of a pointer Rust type fragment corresponds to the overhead introduced by its
concrete Rust types. &inator considers Rc_ to be the most costly, followed by Box_ , ghost_ , mut_ (_),
and shared_ (_). This ordering is strict in order to break ties in case multiple type assignments have
the same cumulative transformation cost. However, there is not necessarily a unique assignment of
interface types that minimizes &inator’s optimality objectives.

Evaluation

We evaluate &inator on three metrics: correctness and precision of inferred Rust interfaces and
run-time performance of &inator.
11.1

Implementation

We implemented &inator’s two top-level components: conversion to source language and constraint generation analysis (Fig. 3).
Conversion to source language. &inator’s conversion from the input C program is implemented
as an LLVM compiler pass preceded by LLVM’s mem2reg optimization to reduce the size and
complexity of the IR [14]. Note that the implementation’s source language supports more features,
such as LLVM IR switch and unreachable instructions, than the version presented in Fig. 4. However,
it does not support function pointers, union types, variadic functions, or ternary operators.
&inator infers source types from LLVM IR, including monomorphic void pointers (i.e., void
pointers cast to a single other pointer type). The implementation cannot handle polymorphic
pointers (i.e., void pointers cast to multiple other pointer types) in general (§3.2). When encountering
polymorphic pointers or unsupported type casts (§3.2), the implementation infers unknown for some
source type fragments, but this may cause constraint generation to fail.
Constraint generation analysis. We implemented &inator’s constraint generation analysis as a
standalone program written in Rust that analyzes the source program and generates SMT constraints.
The analysis uses the Rust z3 crate to generate and solve constraints with Z3 [3].
To improve solving performance, the analysis includes the following optimizations:
• Rust type fragments are factored into separate, independently constrained components.
• Lists of lifetime variables are represented implicitly, without using an SMT datatype.
• Each Loan is represented by the rvalue expression that generates it—there is a one-to-one
correspondence between possible loans and pointer-typed non-nested rvalue expressions.
• Every function and relation the paper presents as defined SMT functions is either inlined, or
declared as an uninterpreted function in SMT and constrained by a set of axioms.
• Superfluous constraints are not generated, e.g., loans from different functions cannot conflict.

Methodology

Our evaluation uses the following C programs as input: the paper’s running example (Fig. 2(a)); the
four smallest programs (in lines of C code13 ) in CRUST-Bench, ulidgen, leftpad, amp, and nandc;
and another CRUST-Bench program, rbtree, because it uses a recursive datatype extensively.
We modified each program by combining multiple files into one source file to simplify inputting
it to &inator. We additionally modified nandc and rbtree slightly to conform to &inator’s current
restrictions without meaningfully changing its functionality, as described later for each program.
To confirm &inator’s translated interfaces were correct, we manually translated each C program
to a (safe) Rust program that used &inator’s interface. To assess precision, we manually translated
each C program to Rust line-by-line and attempted to use the most precise types,14 and compared
this program’s interface to &inator’s interface. For amp and rbtree, we manually translated the
interfaces “blind” (i.e., without looking at &inator’s interface). For the other programs, which
arguably have simpler ownership and borrowing choices, we looked at &inator’s interface first.
Although &inator is correct and precise (according to its cost function) by design, this manual
evaluation of &inator’s inferred interface provides an empirical assessment of these claims.
In addition to the above fully evaluated programs, we evaluated three larger programs from
CRUST-Bench solely for the purpose of measuring &inator’s performance scalability. We initially
selected programs that were closest in size (lines of C code excluding testing code) to 2𝑘 times
larger than rbtree for integers 𝑘 ≥ 1. However, we encountered technical issues—source language
conversion fails amid heavy use of polymorphic pointers and function pointers—with several of
these programs (recordmanager, megalania, and libfor), so we replaced them with the next-closestin-size programs and ended up with the following programs: carrays, jccc, and tisp. We modified
these programs to not use the ternary operator, unions, function pointers, polymorphic pointers,
pointer-to-integer casts, and a few unsupported C library functions that resulted in instructions
that &inator does not currently handle (isdigit, isalnum, and calloc). These changes did not
significantly affect the size of these programs or the complexity of inferring interfaces for them.
To measure &inator’s analysis performance, we summed the wall-clock times for source language translation and constraint generation analysis. We measured &inator’s constraint-solving
performance as the wall-clock time used by Z3 to solve the constraints. To account for running
time variability, we ran &inator on each program five times and reported the average run time.
The experiments ran as jobs on nodes of a Linux cluster with Xeon Platinum 8268 CPUs at
2.9 GHz with 170 GB of RAM. Each run of &inator, which is single-threaded, ran on a dedicated
socket. The experiments used LLVM 17.0.6 and Z3 4.13.3.

Comparison with CRUST-Bench’s Hand-Translated Interfaces

CRUST-Bench provides a hand-translated Rust interface for each benchmark [12], but an apples-toapples comparison with &inator’s interfaces is hard because CRUST-Bench’s interfaces do not
adhere to the same constraints as &inator’s interfaces. Here we provide a qualitative comparison.
Overall, the CRUST-Bench and &inator interfaces are largely the same. They differ in the
following ways, which we group into four categories:

CRUST-Bench’s interfaces are not one-to-one with the C program in a few cases.
• CRUST-Bench’s leftpad interface omits a parameter dest_sz from the leftpad API function.
• CRUST-Bench’s rbtree interface omits from the rbtree struct a sentinel nil field, which the
C program uses to represent node absence, and instead uses Option to allow for node absence.
In contrast, &inator’s interface retains the nil field.
CRUST-Bench’s interfaces are imprecise in a few cases. CRUST-Bench’s rbtree interface uses the type
Rc<RefCell<Node>> for all parameters that were node_t* in C. However, it is possible to correctly
use the less costly &Node or Rc<Node> types for all parameters in exchange for making all and only
the fields of node_t interior mutable, as mentioned in § 11.3. &inator chooses the latter, which
makes the interface, when considered as a whole, more precise.
&inator’s interfaces use less idiomatic types than CRUST-Bench’s types.
• &inator’s interface for ulidgen uses u8 instead of char.
• &inator’s interfaces for leftpad and amp use [u8] instead of str.
• In a similar vein, &inator’s interface for nandc uses &mut i8 instead of &mut bool, due to
LLVM IR not supporting pointers to Booleans (§11.3).
&inator’s definition of interface correctness is more strict than CRUST-Bench’s. Specifically, CRUSTBench’s amp interface uses reference types in places where &inator’s interface uses owned types
because &inator preserves copy semantics (§8). More specifically:
• The return value of decode_arg has reference type &str in CRUST-Bench’s interface, but has
owned type Rc<[Cell<u8>]> in &inator’s interface. The C implementation of this function
copies a string out of the self reference parameter and returns that copy; since &inator
preserves copy semantics, the return type must be owned. Using a reference for the return
value still admits a correct implementation, but that implementation borrows from self
rather than copying out of it, involving different copy semantics.
• Similarly, the buf parameter of decode has reference type &str in CRUST-Bench’s interface,
but has owned type Rc<[Cell<u8>]> in &inator’s interface. The C program assigns self.buf
to an alias of buf; as self.buf is a String in the CRUST-Bench struct interface and buf is a
&str, such an assignment would require copying instead of aliasing. For the same reason
as for decode_arg, a correct implementation of the CRUST-Bench interface is possible, but
would have different copy semantics.
11.5

Summary

The results show that &inator achieves its goals of correctness and precision, modulo its current
limitations. &inator’s performance scales to C programs with thousands of lines of code, but more
work is needed to scale to much larger programs.
12

Conclusion

&inator is a novel constraint-based static program analysis that chooses Rust types for an input
C program that simultaneously satisfy Rust type constraints and preserve semantics. &inator
generates correct, precise interfaces, as our evaluation demonstrates on moderately sized C programs. Scalability to larger programs, relaxing adherence to the C program’s aliasing patterns, and
supporting more C language features remain challenges for future work. This work advances the
state of the art by demonstrating the feasibility of automatic C-to-Rust interface translation, which
can help make C-to-Rust program translation modular, incremental, and tractable.

Rust Types

&inator constrains RTypeFrags by their components: base type (Rust type fragment ignoring
qualifiers and lifetimes), array qualifiers, Cell qualifiers, and lifetime variables. The base types are
enumerated in the BaseType SMT datatype, defined below.
BaseType ∋ 𝛽 ::= unknown | void | bool | i8 | i16 | i32 | i64 | f32 | f64 | struct(𝑠)
| ghost | Box | Rc | shared | mut
In the SMT constraints, each LifeVar is represented by a natural number, and a LifeVar may be
used where a natural number is expected (e.g., as operands of ≤ or as N). We write LifeVar instead
of N to clarify when a natural number should be interpreted as a lifetime variable. &inator’s
constraints represent the RTypeFrag of each TypeLab𝑀 in the following SMT functions and
relations:
(1) BaseType : TypeLab𝑀 → BaseType maps each type label to its base type (i.e., Rust type
fragment ignoring qualifiers and lifetimes).
(2) Array ⊆ TypeLab𝑀 is the set of type labels of Rust type fragments with array qualifiers.
(3) Cell ⊆ TypeLab𝑀 is the set of type labels of Rust type fragments with Cell qualifiers.
(4) RefLT : TypeLab𝑀 → LifeVar maps each type label of a reference Rust type fragment to its
lifetime variable.
(5) StructLT : TypeLab𝑀 × N → LifeVar maps each type label of a struct Rust type fragment
and index 𝑖 to the 𝑖th lifetime variable of the Rust type fragment.

F Computing Source Types from LLVM IR
In LLVM IR, pointer types are opaque; that is, they do not contain information about their referent
type. However, to encode Rust’s type and borrow-checking rules, as well as the semantic preservation rules, &inator needs to know the referent type for each pointer. To recover this information,
&inator’s source language conversion pass performs source type inference.
&inator’s source type inference considers the type information that appears explicitly in LLVM
IR, and uses the relationships between the types of variables, function returns, and struct fields
implied by LLVM IR instructions to infer pointer type information. For example, at the LLVM IR
instruction %v = load i32, %p, &inator’s source type inference determines that the type of %v is
i32, and the type of %v is equal to the type of the referent of %p.
&inator’s source type inference extracts explicit types from struct type definitions, function
declarations, and variable declarations. It extracts equality relationships from LLVM IR instructions
alloca, load, store, getelementptr, call, phi, and ret. Then, it solves for the source types for each
struct field, function return, and variable by solving this system of equalities.
