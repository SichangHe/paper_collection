                                                Abstract. VeriFast is a leading tool for the modular formal verifica-
                                                tion of correctness properties of single-threaded and multi-threaded C
                                                and Rust programs. It verifies a program by symbolically executing each
                                                function in isolation, exploiting user-annotated preconditions, postcon-
                                                ditions, and loop invariants written in a form of separation logic, and
                                                using a separation logic-based symbolic representation of memory. How-
                                                ever, the tool itself, written in roughly 30K lines of OCaml code, has
                                                not been formally verified. Therefore, bugs in the tool could cause it to
                                                falsely report the correctness of the input program. We here report on
                                                an early result extending VeriFast to emit, upon successful verification of
                                                a Rust program, a Rocq proof script that proves correctness of the pro-
                                                gram with respect to a Rocq-encoded axiomatic semantics of Rust. This
                                                significantly enhances VeriFast’s applicability in safety-critical domains.
                                                We apply hinted mirroring: we record key information from VeriFast’s
                                                symbolic execution run, and use it to direct a replay of the run in Rocq.

                                                Keywords: Program verification · Separation logic · Rust.

unsafe fn reverse_iter(original: *mut u8, reversed: *mut u8) -> *mut u8
//@ req llist(original) &*& llist(reversed);
//@ ens llist(result);
{
   //@ open llist(original);
   if original.is_null() { return reversed; }
   let next = *(original as *mut *mut u8);
   *(original as *mut *mut u8) = reversed;
   //@ close llist(original);
   reverse_iter(next, original)
}

unsafe fn reverse(mut list: *mut u8) -> *mut u8
//@ req llist(list);
//@ ens llist(result);
{
   //@ close llist(0);
   reverse_iter(list, std::ptr::null_mut())
}

//@ req true;
//@ ens true;

   }

    This program uses unsafe blocks; therefore, the Rust compiler cannot guar-
antee the absence of undefined behavior. In particular, it cannot guarantee that
the pointer dereferences are safe. Instead, we apply VeriFast1 [7] to verify the
absence of undefined behavior. VeriFast requires that we annotate each function
with a precondition and a postcondition, expressed in a variant of separation
logic [12,14], using a recursive separation logic predicate llist to assert owner-
ship of a linked list of pointer variables. A points-to assertion *P |-> V asserts
ownership of the variable pointed to by pointer P, and that it currently stores
value V. The separating conjunction A1 &*& A2 asserts that A1 and A2 both hold,
separately; the conjuncts must assert ownership of disjoint sets of variables. The
occurrence of &*& in the predicate definition asserts that the linked list is acyclic;
the occurrence in the precondition of reverse_iter asserts that the two linked
lists do not overlap. The right-hand side of a points-to assertion can be a pat-
tern; the pattern ?X binds the pointed-to value to logical variable X, whose scope
extends to the end of the enclosing assertion.

    To verify a program, VeriFast symbolically executes each function separately,
representing memory as a list of so-called heap chunks 2 . A heap chunk is either
a points-to chunk or a predicate chunk. A points-to chunk is either of the form
points_to_(p, s), asserting ownership of a possibly-uninitialized variable pointed
to by pointer p, with initialization state s, or of the form points_to(p, v), asserting
ownership of an initialized variable at p, with value v. Here, p, s, and v are
terms of first-order logic, which may contain symbols (hence symbolic execution).
Declaring a local variable whose address is taken produces (i.e., adds to the
symbolic heap) a points_to_ chunk; assigning to a local variable whose address
is taken consumes (i.e., removes from the symbolic heap, failing if not found)
an appropriate points_to_ chunk and produces a points_to chunk. Calling a
function consumes the callee’s precondition and then produces its postcondition.
Consuming assertion llist(list) fails unless a llist(ℓ) chunk is present in
the symbolic heap, where ℓ is a term that is provably equal to the value of
variable list. To introduce such predicate chunks, the user must generally insert
close p(args); ghost commands into the program, which consume the body of
predicate p and produce a predicate chunk p(args). This process can be reversed
using open p(args); ghost commands. Symbolic execution traces for main and
reverse_iter are shown in Fig. 2.

3   Proof script generation

VeriFast now optionally emits, upon successful verification of a Rust program, a
proof script3 for the Rocq [16] system for developing machine-checked mathemat-
ical proofs, defining constants bodies (a list of all functions of the program, with
their bodies expressed in a slight variant4 of Rust’s Mid-level Intermediate Repre-
sentation (MIR)), preds (a list of all VeriFast predicate definitions), specs (a list
with each function’s precondition and postcondition), and symex_trees (a list
with for each function, a symbolic execution tree containing hints for the Rocq-
encoded symbolic execution algorithm), and a single goal bodies_are_correct
preds specs symex_trees bodies, expressing the correctness of each function
with respect to its specification, with a fixed proof. At least for the example pro-
gram of Fig. 1, the proof goes through, implying that the program is indeed cor-
rect, assuming that bodies faithfully represents the program, that specs faith-
fully expresses the desired correctness properties, and that bodies_are_correct
is sound (discussed in the next section).
    bodies_are_correct5 is essentially a (for now, very incomplete) re-implemen-
tation of VeriFast’s symbolic execution algorithm in Rocq. The main differences
are as follows:

 – VeriFast sometimes performs automation steps. For example, while trying
   to consume a points_to_(ℓ, _) chunk, if no matching chunk is found but a
   points_to(ℓ, v) chunk is found, the latter is auto-opened to obtain points_to_-
   (ℓ, some(v)). To simplify the implementation of bodies_are_correct, these
   auto-steps are explicitly specified in symex_trees.
 – When trying to consume a chunk, e.g. points_to(ℓ, _), if VeriFast finds a
   chunk points_to(ℓ′ , v) in the symbolic heap, it asks an SMT solver whether
   ℓ = ℓ′ . Only if the solver returns Valid does VeriFast consider the chunk to
   match. bodies_are_correct, instead, receives the index k of the chunk that
   should match as a ConsumeChunk(k) hint in symex_trees.
 – VeriFast uses an SMT solver to decide whether the path condition is satisfi-
   able; if not, it abandons the symbolic execution path. bodies_are_correct
   instead receives a Done hint in symex_trees when the path should be infea-
   sible.

bodies_are_correct (at least, in the current state of the system) reduces to a
simple proof goal, intended to be discharged by a simple fixed tactic script that
essentially boils down to repeat (split || intro || congruence || tauto).

4   Soundness
We have proven6 , in Rocq, soundness of bodies_are_correct (the SymEx) with
respect to an axiomatic semantics7 (the AxSem) of VF MIR expressed in Iris
[9], a framework for separation logic in Rocq. The proof justifies the SymEx’s
use of VeriFast predicates and function specifications, and its different treatment
of locals based on whether their address is taken; none of these appear in the
AxSem. The soundness proof is based on a model8 of VeriFast symbolic heaps
in terms of logical heaps, essentially multisets of points_to_ chunks (for now).
The meaning of VeriFast predicates and assertions is defined inductively in this
model, and the soundness of producing and consuming assertions and opening
and closing predicates is proven against it.
    For now, the axiomatic semantics has not itself been validated in any way.
It has one known unsoundness: like VeriFast, for now it ignores StorageLive and
StorageDead MIR statements and considers all locals to be alive throughout the
body. After fixing this, we would like to verify soundness of the AxSem with
respect to one or more other semantics, such as the Radium semantics used by
RefinedRust [6], or a future Rocq encoding of MiniRust [10].

5   Conclusion
In this paper we present a first step towards Foundational VeriFast for Rust,
achieved through Hinted Mirroring, a pragmatic approach that is likely to be
applicable to other verification tools as well. Much work remains to be done,
however, including supporting more Rust features (such as loops, structs, gener-
ics, and unwinding) and more VeriFast features (such as inductive datatypes,
fixpoint functions, lemmas, fractional permissions, and verifying semantic well-
typedness of safe abstractions per RustBelt [8]), and validating our axiomatic
semantics. While our current implementation is minimal, we designed it with the
goal of eventually supporting all of VeriFast, including future VeriFast extensions
relating to Rust’s pointer aliasing rules and relaxed atomics.
    The only existing foundational verification tool for Rust we are aware of is
RefinedRust [6]. Foundational verification tools for other languages include VST
[1,17] and RefinedC [15] for C. All of these, however, are implemented directly
inside Rocq, constraining the user experience and preventing the use of SMT
solvers for high-performance automation.
    Hinted Mirroring is a special case of certificate generation (e.g. [3,2]), and
of oracle-guided result validation (e.g. [11]). However, while there exists work
towards providing foundational backing for non-foundational program verifica-
tion tools (such as for Boogie [13], Why3 [4] and Viper [5]) we are not aware
of existing applications of Hinted Mirroring for separation-logic-based program
verification tools.
