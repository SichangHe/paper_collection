1. Introduction

    Formal veriﬁcation is a mathematical approach to ensuring program correctness by proving that a program conforms to its formal
speciﬁcation. Among the various veriﬁcation paradigms, Hoare-style [1] veriﬁcation has been especially inﬂuential for imperative
languages such as C and Dafny [2]. This approach uses Hoare logic, where the intended behavior of a program is speciﬁed using
logical triples of the form {𝑃 } 𝐶 {𝑄}, denoting that if the precondition 𝑃 holds before command 𝐶, then the postcondition 𝑄 will
hold after its execution. Auto-active veriﬁers employing Hoare-style veriﬁcation such as Frama-C [3] for C and Verus [4] for Rust
allow users to specify speciﬁcations such as preconditions, postconditions, assertions, invariants, and variants. These speciﬁcations
are used to generate veriﬁcation conditions, which are statically discharged by Satisﬁability Modulo Theories (SMT) [5] solvers,
such as Z3 [6], CVC5 [7], and Alt-Ergo [8], enabling rigorous and automated formal veriﬁcation within their respective language
ecosystems.
    C has long dominated low-level systems programming, but its lack of memory safety and weak type guarantees pose signiﬁ-
cant risks. To address these issues, formal speciﬁcation languages and veriﬁcation tools [9–12] have been developed for C, notably
ACSL [13] and the Frama-C platform, which support rigorous veriﬁcation of functional correctness, and the absence of certain unde-
ﬁned behaviors. Meanwhile, the increasing popularity of Rust presents a compelling alternative. Rust oﬀers strong safety guarantees

through ownership and a rich type system. These features eliminate many classes of bugs at compile time. In light of Rust’s strong
safety guarantees, the migration of legacy C codebases to Rust has gained considerable attention. However, to the best of our knowl-
edge, few prior works have explored the feasibility of migrating formally speciﬁed C programs annotated with ACSL, to veriﬁable Rust
while re-establishing formal guarantees via Verus. If such migration is feasible, we can provide strong guarantees about functional
equivalence, signiﬁcantly reducing the need for test cases [14–16] and other equivalence validation approaches [17–19]. Moreover,
while Frama-C oﬀers comprehensive support for functional correctness veriﬁcation, its handling of dynamic memory remains limited,
particularly for operations such as allocation, initialization, and danglingness detection. Consequently, even ACSL-annotated C pro-
grams veriﬁed by Frama-C may not be fully memory-safe. This motivates migrating C programs to veriﬁable Rust, which eﬀectively
complements the guarantees provided by ACSL and leverages Rust’s compile-time checks to ensure memory safety.
    To bridge this research gap, this paper presents the ﬁrst in-depth empirical study on migrating ACSL-annotated C programs to
formally veriﬁed Rust under Verus speciﬁcations. Our study centers on a curated benchmark of 212 C programs, each annotated
with ACSL speciﬁcations. To systematically assess the feasibility of this migration, we developed C2VR (C to Veriﬁable Rust), a semi-
automated framework that handles the migration of both C code and ACSL speciﬁcations. C2VR employs a hybrid migration strategy.
Speciﬁcally, it integrates a large language model for C-to-Rust code translation, while a dedicated rule-based engine performs the
conversion of ACSL annotations into Verus speciﬁcations. This framework enables an end-to-end process where functional behavior
and formal guarantees can be preserved across the language boundary.
    Through applying this framework to our curated benchmark, we empirically investigate not only the extent to which speciﬁcations
can be preserved in Verus, but also the practical challenges that arise during migration. In particular, we identify 15 common
symptoms of migration failure, link these symptoms to 10 underlying root causes, and propose 9 repair strategies to address these
issues.

   of migration failures. Based on these insights, we propose strategies that improve the migration rate.

2. Background & related work

2.1. ACSL and Frama-C

    ANSI/ISO C Speciﬁcation Language (ACSL) is a formal speciﬁcation language designed to annotate C programs with behavioral
contracts such as preconditions, postconditions, loop invariants, and assertions. These annotations enable deductive veriﬁcation of C
programs, allowing developers to reason about functional correctness in a modular and precise manner.
    Frama-C is a widely used open-source platform that supports static analysis and formal veriﬁcation of C code. Its modular architec-
ture provides multiple analysis plugins. In particular, the Weakest Precondition (WP) plugin [20] generates veriﬁcation conditions
(VCs) from ACSL-annotated C programs and translates them into logical goals through the Why3 [21] platform, which then dis-
patches them to backend SMT solvers or interactive provers. The Frama-C/WP toolchain has been successfully applied in safety-critical
projects [22–25].
    The WP plugin performs a memory model encoding of C programs, representing pointers, memory blocks, and separation con-
ditions explicitly in logic. Frame conditions (e.g., assigns clauses) are translated into logical constraints over explicitly modeled
memory regions. Predicates such as \valid and \separated are used to constrain pointer validity and aliasing. This memory-centric
encoding is fundamental to our work, as it reveals the gap between C’s low-level memory state and Rust’s high-level type system. More
speciﬁcally, ACSL speciﬁcations are tightly coupled with the C memory model, where concepts such as raw pointer dereferencing,
aliasing, and separation are directly expressed in logic. However, these constructs do not have one-to-one counterparts in Rust’s safe
subset, which introduces challenges when migrating speciﬁcations.
    As shown in Fig. 1(a), the function KthElement uses ACSL annotations to specify its behavior, including preconditions (lines 7–9),
a frame condition (line 10), and postconditions (lines 11–12). Speciﬁcally, the \separated predicate (line 9) explicitly speciﬁes that
the memory region of arr must not overlap with that of k. The frame condition (line 10) uses assigns to specify that the function is
permitted to modify arr[0.len-1], ensuring other memory regions remain unchanged. The preconditions use the predicate has_kth
(lines 2–3), which speciﬁes write access permission to the memory region occupied by the array segment of length len and the
boundedness of the index k. Since the function contains a loop, loop speciﬁcations (lines 17–20) are added to facilitate the veriﬁcation
process.

2.2. Verus for Rust veriﬁcation

    Verus is one of the most prevalent tools for automated deductive veriﬁcation in Rust. Unlike tools such as Creusot [26] and
Prusti [27] that focus primarily on safe Rust code, Verus supports veriﬁcation of both safe and unsafe code. Therefore, we consider
Verus as a prominent tool and chose it as our study subject. Verus extends Rust with an embedded speciﬁcation language for deductive
veriﬁcation. Unlike ACSL, which is external to C syntax, Verus speciﬁcations are written directly in Rust and coexist with executable
code. To perform veriﬁcation, Verus translates annotated Rust programs into veriﬁcation conditions that are discharged by backend
SMT solvers. This translation leverages Rust’s type system and ownership discipline to restrict aliasing and memory access at the
language level. Owing to its practicality and expressiveness, Verus has been successfully applied to verify large-scale, real-world Rust
systems [28–30].
    Conceptually, Verus programs consist of three code modes: spec, proof, and exec. The spec mode is used to describe properties
about programs; the proof mode contains auxiliary reasoning steps used to assist veriﬁcation; and the exec mode holds the actual
executable implementation. In this paper, we use Verus speciﬁcations to refer to all ghost code written in spec and proof modes, en-
compassing function contract (e.g., requires, ensures, decreases clauses), ghost functions (e.g., spec, proof functions), assertions,
loop invariants, loop variants and proof blocks.
    Verus introduces additional language-level abstractions to improve speciﬁcation expressiveness and SMT compatibility, including
unbounded integer types (e.g., int, nat), and mathematical collection types (e.g., Seq, Map, Set). Verus also provides the @ operator
as syntactic sugar for the view function, which represents the speciﬁcation-level abstraction of an executable object.
    In comparison to ACSL, Verus oﬀers a less expressive speciﬁcation language and lacks direct counterparts to certain ACSL con-
structs, such as inductive deﬁnitions. This absence of one-to-one correspondence requires semantic transformation rather than simple
syntactic translation, which constitutes the fundamental barrier to automated speciﬁcation migration.
    Fig. 1(b) presents the migrated Rust version of the veriﬁed C program, which is successfully veriﬁed by Verus. The requires
clause deﬁnes the precondition (line 9) through a ghost function (lines 3–5) which constrains the slice length and index range, while
postconditions (lines 11–12) specify the expected return value and the side eﬀect. The memory constraints from ACSL, namely the
frame condition (assigns) and memory disjointness (\separated), are naturally enforced in the Verus version by Rust’s mut qualiﬁer
(line 7) and the borrow checker. These mechanisms inherently guarantee exclusive access and memory safety without requiring
explicit logical predicates in the speciﬁcation. The use of the @ operator provides a speciﬁcation-level view of both the slice and
the integer values. Furthermore, loop invariants (lines 17–19) and the loop variant (line 20) are used to describe the behavior and
termination of the loop.

2.3. Migration from C to Rust

   Migration from C to Rust has attracted increasing attention due to Rust’s strong safety guarantees. C2Rust [31] translates C99
code to Rust at scale but relies heavily on unsafe blocks, yielding unidiomatic and less readable output. Several approaches enhance

the safety and quality of C2Rust output. Laertes [32] leverages compiler feedback to infer lifetimes and mutability, replacing raw
pointers with safe references. Emre et al. [33] extend this to broader pointer categories. Ling et al. [34] propose CRustS, which removes
redundant unsafe blocks via structural pattern rewriting. Hong [35] automates the replacement of unsafe constructs, focusing on
lock APIs and output parameters introduced by C2Rust. In later work, Hong et al. further extend this line of work with Nopcrat [36],
which employs static analysis to identify output parameters and replaces them with idiomatic Rust algebraic data types such as
tuples, Option, and Result. They also propose a union transformation approach [37] that converts tagged C unions into Rust enums.
Zhang et al. propose Crown [38], an ownership-guided C-to-Rust translation tool that leverages static ownership analysis to infer
pointer ownership and automatically refactor C2Rust-generated code into idiomatic, memory-safe Rust. GenC2Rust [39] employs
static analysis to extract typing constraints from C void pointers and automatically retypes them into idiomatic Rust generics.
    LLM-based methods have recently shown promise in automating C-to-Rust migration. Shiraishi et al. [40] segment C code into
units, translate them with an LLM, and iteratively repair errors using compiler feedback. Yang et al. [41] use LLMs to generate Rust
from multiple languages, verifying semantics via fuzzing and symbolic execution. Fluorine [42] combines compiler feedback with
diﬀerential fuzzing to test I/O equivalence. Nitin et al. [43] integrate C2Rust with LLM reﬁnement to produce progressively safer Rust.
Zhou et al. introduce C2RustTV [44], which generates high-coverage C test cases via LLMs to validate the functional conformance of
the translated Rust code. Xu et al. [45] leverage data ﬂow graphs to guide type migration, introducing enum indicators and pointer-
type mapping to improve LLM-based C-to-Rust translation at the repository level. Cai et al. propose RustMap [46], a dependency-
guided and LLM-based approach that decomposes project-scale C programs into translation units and iteratively reﬁnes the generated
Rust code via compilation and functional feedback. Hong and Ryu propose Tymcrat [47], which generates candidate Rust signatures
for each C function, provides translated callee signatures to guide LLM translation, and iteratively ﬁxes type errors using compiler
feedback to achieve more idiomatic type migration. Zhang et al. propose RustFlow [48], which utilizes intermediate representations
alongside a multi-stage validation and repair pipeline to generate idiomatic and semantically accurate Rust code.
    Migration from C to Veriﬁable Rust. While prior work has explored C-to-Rust migration, it has largely overlooked the mi-
gration of formally speciﬁed C code with preservation of formal guarantees. Migrating formally speciﬁed programs poses unique
challenges, including mismatches in speciﬁcation languages, misalignment between code and speciﬁcations, and ensuring success-
ful re-veriﬁcation. To address these issues, we propose a novel framework that automates this migration and ensures veriﬁcation
soundness in Rust.

3. Methodology

3.1. Overview

   Fig. 2 outlines the architecture of C2VR, our four-stage migration framework. First, Context-Aware Speciﬁcation Extraction extracts
C code and ACSL speciﬁcations from formally speciﬁed C programs, while recording the contextual positions of each speciﬁcation.
Next, LLM-Driven Code Translation translates the C code into idiomatic Rust using a large language model, with iterative repair guided
by compiler feedback. Then, Type-Guided Speciﬁcation Migration leverages the type information of Rust expressions derived from the
translated code to migrate ACSL speciﬁcations into semantically equivalent Verus speciﬁcations. Finally, Speciﬁcation Embedding and
Manual Fix embeds the migrated speciﬁcations into their corresponding locations within the Rust code, yielding a veriﬁcation-ready
Rust program for the Verus veriﬁer. In cases where veriﬁcation fails, we perform manual intervention by analyzing error symptoms
and applying ﬁxes proposed in Section 4.4.

3.3. LLM-driven code translation

    In this stage, the LLM is employed to translate C code into idiomatic Rust, with a focus on avoiding the use of unsafe keyword.
A key aspect of this translation is the conversion of raw C pointers into semantically appropriate Rust abstractions such as basic
references (e.g., &T, &mut T), slice references (e.g., &[T], &mut [T]), smart pointer (e.g., Box<T>) for heap allocation, and nullable
pointers (e.g., Option<&T>, Option<&mut T>). The translated Rust code is compiled using rustc. If it fails, the error messages and
code are fed back to the LLM for iterative repair until success or a preset limit is reached. Since the output serves as the basis for formal
veriﬁcation, we apply tailored post-processing to refactor the code. The following details our prompting strategy for LLM-based Rust
code generation as well as the post-processing.

3.3.1. Prompt design
    We guide the LLM using few-shot learning with three representative C-to-Rust examples. Including them in the prompt helps the
model learn translation strategies from context, improving output quality. Since the translated Rust code targets formal veriﬁcation,
we impose several constraints to ensure compatibility with the Verus veriﬁer. Below, we outline the primary constraints and explain
their rationale.
    Raw Pointer Restrictions. We prohibit the use of raw pointer conversion methods (e.g., as_ptr(), as_mut_ptr()), casting
references to pointers, and directly using raw pointers (e.g., *const T, *mut T) in the translated code, as Verus lacks support for raw
pointer dereferencing.
    Line-by-Line Fidelity. The translated code must closely mirror the original C structure to maintain veriﬁable correspondence. We
explicitly forbid introducing standard library abstractions or helper functions that encapsulate original logic, as Verus lacks complete
formal speciﬁcations for many standard library methods. Moreover, such abstractions could eliminate the program’s loop structure,
preventing proper embedding of migrated speciﬁcations such as loop invariants.
    Explicit Type Annotations. All variable declarations must include explicit type annotations, as Verus may fail to verify decreases
clauses when type inference is ambiguous.
    Identiﬁer Preservation. All original C identiﬁers (e.g., variable names, function names, struct names) must be preserved to
maintain semantic alignment between translated code and migrated speciﬁcations.

    In addition to the above constraints, external library functions without direct Rust equivalents are handled via Foreign Function
Interface (FFI), which invokes the original C implementation. To preserve veriﬁcation soundness, such functions are treated as external
opaque functions, whose behavior is speciﬁed manually using Verus contracts. These contracts provide the necessary preconditions
and postconditions, enabling Verus to reason about calls to external functions without inspecting their implementations.

3.3.2. Post-processing
    Once the Rust code successfully passes the compiler check, an automated post-processing process within C2VR scans and adjusts
the code to ensure compatibility with Verus. This involves adding the necessary module imports and macros to ensure support
for veriﬁcation-related features. C2VR also annotates static items with exec keyword, as Verus currently does not support their
direct use within speciﬁcations. Finally, function signatures are modiﬁed to allow postconditions to reference return values through
appropriate parameter naming.

3.4. Type-guided speciﬁcation migration

    The speciﬁcation migration involves syntactic transformation and type-guided reﬁnement. As a preliminary step, we implement
an ACSL-speciﬁc parser using ANTLR [50] to generate parse trees for each speciﬁcation. Through depth-ﬁrst traversal of the parse
tree, term-by-term conversion from ACSL to Verus is performed, with structural transformations applied as needed. For instance,
Verus requires slice indexing expressions to use the built-in int type, so arr[i] in ACSL should become arr[i as int] in Verus.
    However, syntactic transformation alone is insuﬃcient to guarantee semantic correctness. The fundamental diﬀerences between C
and Rust type systems require type-aware migration to ensure well-formed speciﬁcations. This necessitates our type-guided approach,
which leverages contextual type information to reﬁne the syntactic transformations.

3.4.2. Type-sensitive migration rules
    During the migration, we pay particular attention to four type-sensitive terms, which are guided by the 𝖤𝗑𝗉𝗋𝖳𝗒𝗉𝖾𝖨𝗇𝖿𝗈 mapping.
    Pre-state Values. Our framework supports a restricted subset of old applications, as speciﬁed in Table 1. In ACSL, the old function
is only used in postconditions to refer to the value of an expression in the pre-state, typically applied to values referenced by pointers
that may be mutated. In contrast, Verus restricts the use of the old function by requiring its argument to be of type &mut T. C2VR
addresses this mismatch through selective application:

 • Preconditions: Since ACSL treats all expressions as implicitly pre-state, C2VR explicitly wraps mutable references with old. For
   instance, an ACSL expression like *e should be migrated to the Verus expression *old(e) when e is a mutable reference.
 • Postconditions: Parse the expression e within old(e) in ACSL, apply Verus’s old function to the sub-expression of e that have

   the type &mut T, and remove the outer old application. For instance, an ACSL expression like old(arr[0]) should be migrated
   to the Verus expression old(arr)[0].

  Dereference Targets. For Verus expressions *e, C2VR uses type information to distinguish between reference and option types,
where the latter represents nullable pointers:

 •   Reference types (e.g., &T, &mut T): Allow direct dereferencing.
 •   Option types (e.g., Option<&T>, Option<&mut T>): Unwrap before dereferencing: *e becomes *e.unwrap().

   Pointers within Memory Permission Predicates. ACSL uses predicates such as \valid(p) and \valid_read(p) to specify
memory access permissions. The predicate \valid_read denotes that a memory region is only readable, whereas \valid indicates
that it is both readable and writable. To soundly migrate these predicates, diﬀerent treatments are required based on target types:

 •   Reference-to-value types (e.g., &T, &mut T): No explicit permission speciﬁcation needed due to Rust’s type system guarantees.

 •   Reference-to-slice types (e.g.,&[T], &mut [T], &str): Migrate range access permission predicates to slice length constraints,
     to ensure soundness of subsequent indexed accesses into the slice. For instance, in ACSL, \valid_read(p+(0.n-1)) should be
     migrated to p.len() >= n in Verus.

    Parameters of Uninterpreted Logical Functions. These functions in Verus arise from migrating two types of ACSL constructs:
(i) inductive deﬁnitions, and (ii) logical function or predicate declarations. Since uninterpreted functions are abstract mathematical
entities without implementations, the migration of their pointer parameter types must be guided by the actual argument types at call
sites.


3.4.3. Ghost function parameter handling
    To determine whether pointer parameters (e.g., int*) in ghost functions should be migrated to slice references (e.g., &[i32])
or value references (e.g., &i32), C2VR performs an interprocedural analysis based on logic functions and predicates. If the pointer
is involved in oﬀset-based dereferencing, C2VR classiﬁes it as array-like and migrates it to a slice reference of type &[T] in Rust.
Otherwise, C2VR treats it as scalar and maps it to a value reference of type &T.
    Moreover, Verus’s strict type checking requires explicit type coercion for ghost function calls, unlike C’s implicit conversions.
Therefore, C2VR looks up the 𝖦𝗁𝗈𝗌𝗍𝖥𝗎𝗇𝖼𝖯𝖺𝗋𝖺𝗆𝗌 mapping to enable accurate type matching and automatic insertion of necessary
type coercions during the migration of ghost function invocations. For instance, given the migrated Verus ghost function pub
uninterp spec fn is_fibo(n: int, r: int) -> bool, C2VR adds mappings (is_fibo, 0) -> int and (is_fibo, 1) -> int
to 𝖦𝗁𝗈𝗌𝗍𝖥𝗎𝗇𝖼𝖯𝖺𝗋𝖺𝗆𝗌. Subsequently, calls to is_fibo(n, m) are automatically rewritten as is_fibo(n as int, m as int) by query-
ing 𝖦𝗁𝗈𝗌𝗍𝖥𝗎𝗇𝖼𝖯𝖺𝗋𝖺𝗆𝗌 for each parameter’s type. In Verus, uninterp spec fn declares an uninterpreted ghost function, which is treated
as an abstract logical symbol without implementation. It is used purely at the speciﬁcation level, and Verus reasons about it only
through its signature and provided axioms.


3.4.4. Encoding C speciﬁcations via Rust language mechanisms
    A key diﬀerence between ACSL and Verus lies in how each framework leverages the underlying programming language features
to express formal speciﬁcations, particularly concerning memory safety and aliasing.
    ACSL, designed for C programs, relies heavily on explicit annotations to capture memory permissions, separation, and eﬀects.
These are necessary for C’s memory model, but lead to substantial annotation overhead and complexity. In contrast, Verus leverages
Rust’s type system and borrow checker to enforce strict aliasing rules. These rules prevent the coexistence of mutable and immutable
references to the same object, eﬀectively encoding pointer separation. As a result, Verus reduces the need for the explicit and often
verbose separation annotations required in ACSL.
    Moreover, Rust’s distinction between immutable and mutable references naturally encodes memory read and write permissions.
Immutable references guarantee read-only access, while mutable references allow modiﬁcation. This aligns with the speciﬁcation of
memory readability and writability in formal annotations. Additionally, the mut qualiﬁer in Rust acts as an implicit frame condition,
indicating which parts of memory a function or loop may modify. Consequently, Verus can express side-eﬀect scopes more succinctly
and precisely, leveraging Rust’s type system to capture frame conditions without extensive manual annotation.
    When migrating C string pointers (e.g., char*) denoting null-terminated strings into string slice references in idiomatic Rust (e.g.,
&str), an important semantic gap arises due to diﬀerences in string termination conventions. In C, the eﬀective length of a string is
implicitly determined by the ﬁrst occurrence of the null terminator (i.e., \0), whereas Rust relies on explicit length information to
determine string boundaries and treats \0 as a regular character. To faithfully preserve the original semantics, ACSL predicates for
string pointer validity, such as \valid_read(s+(0.strlen(s))), are replaced with Verus speciﬁcations that require the string slice
to be one character longer than the C string and that all characters except the last are non-null. This substitution is enabled by Rust’s
memory-safe type system and the explicit length information inherent in string slice references. Furthermore, strlen(s) in ACSL
must be migrated to s.len()-1 in Verus, representing the length of the string slice excluding the null terminator.


3.4.5. Migration of non-trivial ACSL constructs
   The majority of ACSL constructs covered by our benchmarks have direct one-to-one correspondences in Verus, making speciﬁcation
migration trivial. However, we identiﬁed four key patterns in which Verus currently falls short of representing certain ACSL constructs.
For two of these patterns, we devised workarounds to enable migration, while the remaining two remain non-migratable.
   Patterns Enabled by Workarounds. Two patterns were successfully migrated through automated workaround strategies in C2VR,
which employ speciﬁc transformation rules. These patterns are (1) inductive deﬁnitions, and (2) ghost code.

 • Inductive Deﬁnitions. Inductive deﬁnitions in ACSL have no direct counterpart in Verus. As shown in Fig. 3(a), an ACSL inductive
   deﬁnition speciﬁes base and inductive cases using the inductive keyword. To handle this in Verus, C2VR extracts the function
   signature from the deﬁnition and creates an uninterpreted ghost function, as illustrated in Fig. 3(b). Each case of the inductive
   deﬁnition is then treated as an axiom and added to the current veriﬁcation scope.
 • Ghost Code. Verus has limited support for ghost code, particularly loops within ghost blocks. As illustrated in Fig. 4(a), the

   ghost code contains a loop together with a corresponding loop variant to ensure termination. C2VR handles this by applying
   the deghosting procedure described in Section 3.2, which transforms ghost code into ordinary ACSL-annotated C fragments. The
   resulting code can then be migrated and veriﬁed in Verus, as shown in Fig. 4(b).

4. Evaluation

     The experiments aim to answer the following research questions:

 • RQ1: What is the eﬀectiveness of C2VR, the migration framework proposed in this study?
 • RQ2: Does the speciﬁcation migration in C2VR preserve the semantics of ACSL speciﬁcations, and to what extent does it reduce
   speciﬁcation eﬀort via Rust’s language mechanisms?

4.1. Evaluation setup

    Benchmark. We curated a benchmark to evaluate our framework, consisting of 212 C programs annotated with ACSL speciﬁcations
from four distinct sources: tutorial_wp [52], frama-c-problems [53], LMS-Verify [54], and AutoSpec [55]. Each benchmark program
corresponds to a single C source ﬁle containing one or more functions with ACSL annotations. The programs were carefully selected
and, when necessary, modiﬁed with additional speciﬁcations to meet the stricter veriﬁcation standard of this study, which ensures the
absence of runtime errors such as arithmetic overﬂow and out-of-bounds array access. During the curation process, we also conducted
manual ﬁltering to identify and remove redundant programs, ensuring each included case represents a non-overlapping logic scenario.
Moreover, programs lacking speciﬁcations were excluded. In addition, the benchmark includes two specially crafted programs of
signiﬁcant scale, containing over 900 and 1300 lines of code respectively. Notably, according to the Frama-C/WP Manual [20],
our benchmark covers nearly all standard WP-supported constructs, with the sole omission of the exits clause. The details of the
benchmark, including the number of programs, lines of code, and the number of four speciﬁcation types, are summarized in Table 2.
Moreover, the benchmark encompasses diverse C language features, including user-deﬁned types (e.g., structs, enums, and unions),
nested pointers, function pointers, and calls to standard C library functions.
    Experimental Conﬁguration. C2VR comprises approximately 14,000 lines of code, primarily implemented in Python. Exper-
iments were conducted on Ubuntu 22.04 with Rust 1.87. For the migration, we used diﬀerent models including DeepSeek-R1,
Qwen series, and Llama series models during the C-to-Rust translation. The models were conﬁgured with the following parame-
ters: temperature set to 0.2 and top_p set to 0.7. For models that support thinking mode, this mode was enabled by default with
max_tokens set to 16384; otherwise, max_tokens was set to 2048. The maximum number of iterative repair rounds in the translation
process was set to 3. Lastly, we employed Verus (version 0.2025.06.14) to verify the Rust code, with Z3 and CVC5 as the underlying
solvers.

4.2.2. Impact of type-guided speciﬁcation migration
    We conducted an ablation study by removing the type guidance component, performing speciﬁcation migration based solely
on ACSL constructs without leveraging type information from the LLM-translated Rust code. As shown in Table 4, in the absence of
human-in-the-loop, type-agnostic migration achieved substantially lower success rates: 71/175 (40.57%) at the ﬁle level and 159/415
(38.31%) at the function level, compared to 92/175 (52.57%) and 212/415 (51.08%) respectively with type guidance enabled.
    The analysis of type-agnostic migration failures uncovered ﬁve critical issues within the migrated speciﬁcations. First, 23 pro-
grams encountered type mismatches in old function applications due to incorrect parameter types, as the function expected mutable
references (&mut T) but received other types. Second, 2 programs lacked the necessary application of the old function to mutable
references in preconditions. Third, 21 programs exhibited semantic misalignment between ACSL memory permission predicates and
the mutability of corresponding Rust references in LLM-translated code. Fourth, 2 programs incorrectly treated Option<&i32> types
as direct references, attempting dereferencing without proper unwrapping. Finally, 7 programs failed due to type mismatches in calls
to user-deﬁned ghost functions with incompatible argument types.
    These failures stem from two fundamental challenges in speciﬁcation migration. First, expressiveness diﬀerences between ACSL
and Verus require contextual adaptation. For instance, ACSL implicitly treats precondition values as pre-state, whereas Verus de-
mands explicit old function applications. Second, ACSL speciﬁcations sometimes inaccurately reﬂect C program semantics, such as
using \valid predicates for read-only pointers where \valid_read would be more precise. The LLM’s code comprehension capabil-
ities enable it to accurately capture code semantics, translating read-only pointers into immutable references. Building on the type
semantics of the LLM-translated Rust code, our type-guided approach improves the well-formedness of migrated Verus speciﬁcations,
thus resolving the two challenges discussed above.

emits Rust library calls (e.g., wrapping_add, wrapping_mul) that Verus’s standard library does not yet support; (2) semantic over-
approximation: C2Rust conservatively translates const and pointer types into mutable forms, losing immutability information. Beyond
these technical issues, the unidiomatic Rust code produced by C2Rust increases manual repair eﬀort, making veriﬁcation far more
cumbersome compared to the idiomatic code generated by LLM-based engines.



4.2.4. Impact of speciﬁcation-guided code translation
    We conducted a comparative experiment to evaluate whether ACSL speciﬁcations can facilitate successful migration. As shown
in Table 4, speciﬁcation-guided translation slightly underperformed the speciﬁcation-agnostic setup, yielding 82 compared to 92
ﬁle-level passes and 186 compared to 212 function-level passes.
    Based on our analysis, two factors underlie this performance drop. First, LLMs occasionally introduce standard Rust macros such
as debug_assert!() and assert!(), which are intended to encode ACSL clauses such as ensures and loop invariant, even though
these assertions should not be part of the translation. However, Verus does not support these runtime macros for formal veriﬁcation
and only accepts Verus-speciﬁc assertion statements. Second, ACSL assigns clauses and \valid predicates can lead LLMs to mark
references as mutable even when the referenced data actually remains unchanged. This imposes an increased veriﬁcation burden in
Verus, typically requiring supplemental invariants that are redundant for immutable references.
    Answer to RQ1: Our migration framework successfully and automatically migrated 92 out of 175 formally speciﬁed C programs
to veriﬁed Rust programs, with type-guided speciﬁcation migration signiﬁcantly enhancing the migration eﬀectiveness. Model choice
critically aﬀects performance, with advanced LLMs (e.g., DeepSeek-R1, Qwen3-235B-A22B) achieving superior results. Moreover, using
advanced LLMs as the translation engine achieves substantially better migration outcomes than C2Rust.



4.3. RQ2: empirical validation of speciﬁcation migration

   Motivation. To ensure sound migration from ACSL-annotated C programs to Verus-annotated Rust programs, it is essential that
ACSL speciﬁcations can be equivalently expressed in Verus. Thus, validating the correctness of speciﬁcation migration is crucial.
   Method. We conducted an empirical evaluation to assess the correctness of our speciﬁcation migration and the accompanying
reduction in speciﬁcation burden. (1) Semantic Consistency Validation: To evaluate semantic preservation, we performed speciﬁcation-
based testing on a set of benchmark programs. We constructed Rust test harnesses to check whether the migrated Verus speciﬁcations
consistently preserved the original semantic intent and correctly distinguished between valid and invalid inputs. (2) Speciﬁcation
Reduction via Language Guarantees: Our migration framework speciﬁcally accounted for Rust’s inherent language-level advantages in
expressing memory safety and aliasing properties. We quantiﬁed the reduction in speciﬁcation burden by measuring the number of
predicates eliminated due to Rust’s type system and ownership guarantees.

S. Xia, Y. Ou, C. Su et al.                                                                  Science of Computer Programming 254 (2026) 103535


4.3.1. Semantic consistency validation
   We conducted a speciﬁcation-based testing experiment to verify that the migrated Verus speciﬁcations faithfully represent the
original ACSL intent.

 • Sampling Strategy. To ensure a representative evaluation, we selected 100 benchmark programs for manual validation. This
   sample includes approximately half of the successfully migrated programs (64 programs) and all of the failed migration cases,
   covering all ACSL constructs present across the complete benchmark set. By including the entire set of failed migrations, we can
   rigorously determine whether the failures originated either from errors in code translation and speciﬁcation migration, or from
   other factors.
 • Testing Methodology. For each benchmark, we generated test cases using the logical boundaries of the original ACSL requires

   clauses as the ground truth. On average, we constructed seven valid cases that satisfy the source preconditions and two invalid
   cases that violate them per function. We then manually developed Rust test harnesses to execute these cases. To enable dynamic
   testing, we instrumented the migrated code by converting loop annotations and intermediate assertions into runtime assertions.
   This setup allowed the harness to verify that migrated requires clauses correctly ﬁltered inputs, that intermediate states remained
   consistent with the original logic, and that the migrated ensures clauses correctly validated the correspondence between the inputs
   and expected outputs deﬁned in the test cases.
 • Runtime Assertion Instrumentation. We manually convert Verus assertions into Rust runtime assertions while preserving their

   semantics in two main aspects. (1) Integer arithmetic: since Verus uses unbounded integers, we lift all operands in integer arith-
   metic expressions to arbitrary-precision integers using the num-bigint [61] crate to avoid overﬂow-induced unsoundness. (2)
   Memory-related properties: memory-related assertions concern slice bounds (e.g., p.len() >= n), which can be directly trans-
   lated into Rust assertions since they have direct semantic counterparts.
 • Validation Criteria. A migration is deemed semantically correct only if: (i) the migrated requires clauses correctly distinguish

   between valid and invalid inputs, and (ii) for all valid inputs, all intermediate runtime assertions derived from loop annotations
   and assertions are satisﬁed during execution and the ﬁnal outputs satisfy the migrated ensures clauses.

   Based on these validation criteria, the migrated speciﬁcations preserved semantic consistency across all 100 sampled benchmark
programs. This empirical evidence conﬁrms that our framework accurately maintains the original intent of the speciﬁcations. Fur-
thermore, our evaluation exhaustively covered all programs that were not successfully migrated and veriﬁed. As no mismatches were
detected during their execution against the translated code, we conﬁrm that these migration failures did not result from errors in
code or speciﬁcation translation. A detailed root-cause analysis of these instances is provided in Section 4.4.

4.3.2. Speciﬁcation reduction via language guarantees
   We quantiﬁed the extent to which Verus leverages Rust’s type system to simplify speciﬁcations. Unlike ACSL, which requires
explicit and verbose annotations for memory permissions and separation, Verus utilizes Rust’s ownership and borrowing rules to
encode these properties implicitly.

 • Implicit Encoding. In the migrated programs, Rust’s mutable and immutable references naturally encode read and write permis-
   sions as well as aliasing constraints. Furthermore, the mut qualiﬁer serves as an implicit frame condition, which eliminates the
   need for manual side-eﬀect annotations.
 • Quantitative Impact. By leveraging these language-level features, our framework successfully eliminated 100 of the 332 memory

   permission predicates, 68 separation predicates, and 409 frame conditions from the benchmarks.

   Answer to RQ2: Our evaluation conﬁrms that the migration framework accurately preserves the semantic intent of the original
speciﬁcations and signiﬁcantly reduces memory-related speciﬁcation overhead by leveraging Rust’s type system.

4.4. RQ3: diagnosis and resolution of failures

   Motivation. To explore potential solutions for migration failures, it is essential to investigate the observed error symptoms and
analyze the underlying root causes.
   Method. Based on the best migration results in Section 4.2.3, we manually examined the 83 unsuccessfully migrated programs and
categorized their failure symptoms into three patterns: Translation Misalignment, Compilation Errors, and Veriﬁcation Errors. Translation
misalignment refers to cases where LLM-generated Rust code diverges from the original C program, resulting in inconsistencies with
the Verus speciﬁcations. Compilation Errors encompass symptoms where the Rust code with embedded Verus speciﬁcations fails Verus
compiler validation. Veriﬁcation Errors include symptoms where the code compiled successfully but fails during formal veriﬁcation.
For each category, we detail the speciﬁc errors encountered and count their frequency. We further manually analyze the underlying
causes of these errors and propose feasible remediation strategies. The distribution of these symptoms is shown in Fig. 7.

4.4.1. Translation misalignment
    This issue accounted for 2 symptom types across 5 programs. (1) Variable Missing: 3 programs experienced speciﬁcation lookup
failures due to missing variables, including 1 program where LLM translation eliminated the variable and 2 programs where variable
names were modiﬁed. (2) Method Unavailability: The remaining 2 programs encountered this issue where speciﬁcations applied
methods unavailable to the translated variable types, caused by LLM altering C variable types during translation despite preserving

overall function behavior. These two errors stemmed from two distinct root causes. (1) Untranslatable C constructs: Due to syntactic
and semantic gaps between C and Rust, perfect alignment was often infeasible. Constructs like goto lacked direct Rust equivalents,
prompting control ﬂow restructuring that sometimes omitted variable declarations, resulting in undeﬁned variables in speciﬁcations.
(2) Loss of syntactic and type ﬁdelity: The LLM prioritized functional equivalence over strict syntax and type ﬁdelity, leading to variable
renaming and type changes despite prompt guidance. Resolving misalignment requires adjusting variables to match speciﬁcation
expectations.

4.4.2. Compilation errors
    This failure category was the most prevalent, accounting for 5 symptom types across 45 programs. (1) Type-Related Errors: A
total of 18 programs encountered type-related compilation errors. First, 9 programs experienced incompatibilities due to improper
cross-usage of primitive types (e.g., i32, char, bool), where expected and found types did not match. Additionally, 6 programs
encountered errors from attempting size comparisons between non-integer types. Another 5 programs failed when trying to add
reference type variables with integer values, expecting pointer arithmetic similar to C programs where pointer values are combined
with oﬀsets to obtain references to target memory locations. Finally, 1 program exhibited type errors when performing arithmetic
operations between characters. (2) Verus Feature Limitations: This symptom manifested in 18 programs. Several unsupported Rust
features caused compilation errors, including division or modulo operations on signed ﬁnite-width integers (8 programs), usage of
mutable static variables (4 programs), limited usage of mutable references (3 programs), indexing operations on strings (1 program),
and unsizing operations on arrays (2 programs). (3) Extern Variable Usage: Limitations on accessing variables through the foreign
function interface (FFI) led to failures in 3 programs. (4) Naming Conﬂicts: 4 programs failed due to identical names shared by
executable and ghost functions. (5) Standard Library Gaps: 2 programs failed because Verus lacked speciﬁcations for required Rust
standard library methods.
    Our analysis revealed three fundamental root causes underlying the observed compilation failures. (1) Cross-Language Type System
Divergence: ACSL is based on the C type system that allows implicit conversions between integer, Boolean, and character types, while
Verus adheres to the strict Rust type system that prohibits almost all such implicit conversions. Speciﬁcally, Verus does not support
type coercion from integers or characters to Booleans, but the reverse is allowed. Additionally, although Verus supports comparisons
between character and integer types, function parameter passing still requires explicit type coercion to avoid mismatched type errors.
Furthermore, C allows arbitrary memory manipulation through pointers, whereas Rust’s references are designed to ensure memory
safety and prevent such operations. (2) Inconsistent speciﬁcation naming conventions: ACSL’s naming conventions allow executable and
logic functions to share identiﬁers, which conﬂicts with Verus’s requirement for distinct names of executable and ghost functions.
(3) Immature veriﬁcation infrastructure: Verus currently provides incomplete support for standard Rust features, limiting its ability to
fully handle translated code from C.
    Based on the above causal analysis, we developed three strategies speciﬁcally aimed at resolving type-related errors and naming
conﬂicts. (1) When Booleans are expected but integer or character expressions are provided, conversions are performed using nonzero
checks. (2) For other cross-usage scenarios involving these three types, explicit type coercion is applied. (3) Naming conﬂicts between
executable and ghost functions are resolved by renaming ghost functions to eliminate duplicates.

    We identiﬁed ﬁve primary causes underlying the observed veriﬁcation failures. (1) Limited veriﬁcation capabilities: Verus demon-
strated weaker veriﬁcation power compared to Frama-C verifying ACSL, particularly evident in nonlinear operations involving mul-
tiplication or division. Verus failed to verify the equivalence of built-in collection types (e.g., Seq, Set, Map) via the ordinary equality
operator in cases where the collections were constructed diﬀerently. (2) Absence of valid trigger terms in quantiﬁed predicates: Veri-
ﬁcation and use of quantiﬁed predicates both required triggers, which must be either automatically inferred by Verus or explicitly
annotated by us. However, Verus permitted only function calls, ﬁeld accesses, or arithmetic operators as valid trigger terms. When
such syntactic forms were absent in quantiﬁed predicates, Verus failed to infer triggers automatically. Moreover, proving universally
quantiﬁed predicates required explicit triggers, even though these triggers occasionally oﬀered no beneﬁt to later veriﬁcation. (3) Slice
out-of-bounds access: Indexing into slices that were accessed via mutable references inside loops failed to guarantee that the indices
remained within valid bounds. (4) Loop variant divergence from ACSL: ACSL permits negative loop variants post-termination, while
Verus requires non-negativity throughout, causing termination proof failures. (5) Lack of termination speciﬁcations for ghost recursive
functions: Verus requires termination veriﬁcation for ghost recursive functions, unlike ACSL. As a result, migrated Verus speciﬁcations
often lacked these speciﬁcations, leading to veriﬁcation failures.
    To address these veriﬁcation errors, we conducted an in-depth analysis to distill ﬁve general mitigation strategies.

1. To compensate for Verus’s limited veriﬁcation capabilities, it is necessary to supplement the migrated speciﬁcations with additional
   proof annotations such as loop invariants, assertions, and auxiliary ghost functions.
2. When Verus cannot infer triggers for quantiﬁed predicates, users must explicitly annotate trigger terms to guide instantiation. If
   no valid triggers exist, a custom ghost function can replace terms with function calls to make them triggerable. These calls should
   be reintroduced through extra proof annotations, as Verus requires explicit pattern matches to instantiate bound variables.
3. To prove bounds safety for slice access via mutable references within loops, relevant slice length predicates from function precon-
   ditions should be incorporated into the loop invariant.
4. To address the divergence in loop variant semantics, a suﬃciently large positive constant (e.g., u128::MAX) should be added to
   the loop variant to guarantee non-negativity throughout the loop’s execution.
5. When ghost recursive functions lack termination speciﬁcations, decreases clauses must be explicitly annotated. Additionally,
   since Verus only unfolds recursive functions once by default in the SMT solver, proof annotations with the reveal_with_fuel
   directive are required to specify the number of recursive calls that the SMT solver can spawn during veriﬁcation.

   Based on the ﬁve solutions described above, we manually repaired 39 programs that exhibited veriﬁcation errors, including 7
programs that still failed veriﬁcation after ﬁxing translation misalignment errors and compilation errors. All these programs were
eventually veriﬁed successfully, demonstrating the generality and eﬀectiveness of our proposed solutions.

and develop 9 repair strategies that successfully repair 47 programs.

5. Discussion

5.1. Implications

   Based on the results of the research questions, we outline four key implications for veriﬁed program migration.
   Migration Framework Design Involves Fundamental Trade-oﬀs. The design choice between classical automatic approaches
and LLM-based approaches involves fundamental trade-oﬀs between semantic preservation, veriﬁcation friendliness, and engineering

                                                                                15
S. Xia, Y. Ou, C. Su et al.                                                                 Science of Computer Programming 254 (2026) 103535


eﬀort. The classical automatic approach aims to preserve semantics through conservative translation strategies, but this comes at the
cost of veriﬁcation friendliness. Speciﬁcally, this approach suﬀers from speciﬁcation gaps introduced by unspeciﬁed functions (e.g.,
wrapping_add) in the veriﬁcation environment, and from semantic over-approximation caused by conservatively translating global
variables and pointers into mutable representations, which requires whole-program alias and dataﬂow analysis to infer the original
immutability of variables. In contrast, the LLM-based approach achieves reasonably eﬀective migration results with considerably
lower engineering eﬀort and expertise, making it a more practical alternative.
    Speciﬁcation-Code Alignment Is Critical. Beyond ensuring the correctness of code and speciﬁcation migration independently,
maintaining their alignment poses signiﬁcant challenges. Our type-guided speciﬁcation migration approach eﬀectively mitigates
certain misalignment issues. However, our analysis of migration failures reveals residual misalignment issues, suggesting the need
for more precise and sophisticated program analyses techniques to guarantee speciﬁcation-code alignment.
    Speciﬁcation Language Diﬀerences Introduce Both Beneﬁts and Barriers to Migration. Our comparative analysis of ACSL
and Verus reveals that Verus signiﬁcantly reduces memory-related speciﬁcation burden due to Rust’s inherent safety guarantees.
Nonetheless, we identify two categories of non-migratable ACSL patterns, highlighting gaps in Verus’s expressiveness. This motivates
two future directions: extending Verus’s speciﬁcation language and designing semantically equivalent workarounds. Beyond pure
expressiveness, a signiﬁcant challenge remains in achieving idiomatic speciﬁcation migration. Speciﬁcally, our tool currently mi-
grates ACSL inductive deﬁnitions into broadcast proof functions to ensure axiomatic consistency and structural generality. While
functional, this approach may lack the idiomatic feel of recursive spec functions in Verus. Future work could explore techniques to
automatically derive recursive computational logic to enhance readability.
    Systematic Failure Analysis Enables Automated Repair. Our systematic analysis of migration failure causes and the proposed
manual repair strategies establish a foundation for automating failure recovery. However, these strategies are not suﬃcient to address
all migration issues, such as unsupported features, FFI, and standard library methods. These unresolved failures expose existing
limitations and motivate the pursuit of innovative repair approaches.


5.2. Threats to validity

    Internal Validity. The generation of the LLM for code translation is non-deterministic. Although we set the temperature to
0.2 to minimize output diversity, the inherent randomness in LLM inference may still introduce variability in translation results.
Additionally, the LLM may produce incorrect or imprecise type translations, which could confound our evaluation of the framework’s
eﬀectiveness.
    External Validity. First, the benchmark used in our study may not be representative enough to generalize to real-world migration
scenarios due to its limited size. Second, the LLM employed for C-to-Rust translation may not generalize to other language models,
future versions, or diﬀerent conﬁgurations, as the model’s behavior and performance are subject to continuous updates and variations.
This could lead to the ﬁndings and analysis based on the LLM’s translation results being non-generalizable to scenarios involving other
LLMs. Moreover, the speciﬁcation migration component in our framework currently supports only a subset of ACSL, including a limited
set of memory-related predicates (\valid, \valid_read, and \separated), potentially causing migration failures when encountering
unsupported syntax (e.g., statement contracts, \initialized) in actual projects. These limitations may aﬀect the broader applicability
of our ﬁndings to diverse veriﬁcation migration contexts.


6. Conclusion

    This paper presents the ﬁrst empirical study on migrating formally speciﬁed C programs to veriﬁable Rust. In this paper, we design
C2VR, a migration framework that automates the migration of C code and ACSL speciﬁcations, leveraging Verus for ultimate veriﬁ-
cation of Rust. Without human intervention, the framework successfully migrates 92 programs. After applying the ﬁxing strategies
described in Section 4.4, the total number of successfully veriﬁed programs increases to 139, reaching the ﬁnal success rate of 79%.
Our empirical analysis reveals key expressiveness gaps between ACSL and Verus, as well as identiﬁes diverse migration errors and
root causes. And we propose eﬀective ﬁxes to improve the migration rate.
    Overall, this work highlights the feasibility of automatic migration from C to veriﬁable Rust, and oﬀers a concrete foundation for
future work on scaling veriﬁed software migration across language boundaries.
