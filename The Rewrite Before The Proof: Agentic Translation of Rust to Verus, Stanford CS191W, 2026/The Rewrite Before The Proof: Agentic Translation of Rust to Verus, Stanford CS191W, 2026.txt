                                                                   Abstract
          Pushing production Rust through Verus requires mechanical refactoring rather than proof-theoretic engineering: com-
      pound assignments must become named locals, subtle::Choice operations need explicit wrappers, and iterator chains
      must be converted into indexed loops with hand-written loop invariants. Though structurally simple, these rewrites are
      a strict prerequisite to discharging proof obligations. We evaluate an agentic pipeline automating this translation step on
      CURVE 25519- DALEK using a benchmark of 107 cleaned rewrite obligations drawn from 133 hand-classified sites across
      14 files of the Verus-verified DALEK - LITE fork. The agent splices candidates into a live worktree, runs cargo verus
      focus, classifies errors into 12 buckets, resolves missing imports, and executes up to three repair turns. We compare three
      methods: a nearest-neighbor retrieval baseline (NN), a single prompt with a 17.6 kB SKILL context (M1), and a pattern
      router with specialized prompts (M2). Hand-judging 228 translation attempts reveals our ground-truth judge achieves 1.000
      precision and 0.600 recall (95% CI [0.39, 0.78]). Crucially, 134 of 160 verify-passing LLM attempts generate correct
      executable bodies but omit the load-bearing ensures clause (NEQ-FIXABLE). Augmenting the SKILL context with 60
      lines of specification instructions fixes this, flipping 4/10 previously failing cases to whole-crate verification pass (3/3 under
      clean splicing). Headline rates (NN/M1/M2) are: verify-pass (31.8%/29.0%/27.1%), near-equivalent (28.0%/33.6%/33.6%),
      and raw GT-match (6.5%/0.9%/1.9%; corrected upper bounds: 10.9%/1.6%/3.1%). Finally, ∼50% of failures across all
      methods never reach the prover, rejected early by the splicer, parser, resolver, or lifetime checker, proving the verification gap
      is heavily bound to infrastructure.

1    Introduction
Decades of work on systems such as seL4 [4], CompCert [5], and IronFleet [6] have shown that critical software can be
machine checked, provided the system is written in a verification aware dialect from day one. Verus [1] carries that discipline
into Rust by combining linear ghost types with Z3 [7] such that a single language can hold both the program and its proof.
The catch is that not every Rust program is a Verus program: iterator chains, closures, operator overloads on user types,
tuple struct projection, and compound assignment (acc += a * b) either fail to lower into the verifier IR or hand Z3 a
quantifier instantiation problem that it cannot finish in time. This is the thesis of the paper: formal verification of production
code has a translation-layer problem, not only a proof-generation problem. Before any proof obligation can be discharged,
the source must be mechanically rewritten into the verifier’s accepted dialect, and for Verus it is that rewrite, not the proof,
that bottlenecks adoption.
    Existing LLM driven verifiers such as AutoVerus [2], VeruSAGE, and VeruSyn [3] attack the proof half and benchmark
only on inputs already inside the verifier’s accepted dialect. These collapse when applied to raw upstream Rust because the
model dutifully writes proof annotations around code that the front end refuses to lower. This paper isolates the prerequisite
step by asking the LLM to restructure the code so that a downstream prover can succeed, rather than to write the proof itself.
    The instantiation uses CURVE 25519- DALEK [8] and its Verus verified fork DALEK - LITE. Diffing the two yields 133
paired rewrite sites across 14 files, which we sorted into 12 pattern categories (R1–R12); 107 of those rows survive cleaning
and form the headline benchmark (Sec. 4). The agent (Sec. 5) splices a candidate into a real git worktree, runs cargo
verus focus, buckets the failure category, retries imports when a symbol is missing, and runs up to three repair turns.
Three methods then feed that loop: NN, the zero LLM retrieval floor; M1, a single prompt anchored to a 17.6 kB SKILL
document; and M2, a router that dispatches each case to per pattern specialist prompts.
    The single most actionable finding is that the agent almost always writes the correct executable body and almost never
writes the specification annotation the verifier needs: the gap between “compiles and verifies” and “matches ground truth” is
one missing transformation. The data, more concretely:
 • The strict GT-match gap has a precise location: of 160 verify passing LLM attempts the judge calls NEQ, 134 are
   NEQ FIXABLE, meaning the body matches ground truth and only the ensures/proof block is missing. The agent’s
   dominant failure mode is mechanical, not semantic.
 • Verify is a near tie at NN 31.8%, M1 29.0%, and M2 27.1%, inside a 5 pp band, with the ordering flipping per pattern.
 • The spec aware near equivalent metric (hand judged) gives the LLM the win at the case level (33.6% vs. 28.0%) and by a
   much wider margin at the attempt level (93% vs. 68%).

2    Related Work
Verus and verified Rust. Verus [1] adds ghost code and an SMT backed verification condition generator to Rust. Its
accepted subset is documented but ordinary Rust syntax does not enforce it, and the differences are substantive: no closures,
no iterator combinators, restricted trait dispatch, no copy from slice on slices, and a long tail of smaller restrictions.
Moving a crate into this subset is engineering work that the compiler does not help with.

LLMs for proof annotation. AutoVerus [2] was the first verifier in the loop approach to generating loop invariants and
requires/ensures clauses, and its benchmark consisted of small algorithmic programs. VeruSAGE added an observation
reason act loop that patches proofs after SMT failure, and VeruSyn [3] addresses training data scarcity by synthesising
verified Verus programs. What these systems have in common is that the input has already been moved into the verifier’s
accepted dialect.

Code translation with LLMs. A separate line of work uses LLMs as code to code translators (Python→Rust, C→Rust,
and similar). The task in this paper is a translation within Rust whose acceptability depends on a downstream SMT solver, so
the standard metrics (BLEU, exact match, compile pass) do not capture what we want to measure. The ranker is lexicographic
on (verifies, compiles, equiv).

Pipeline tuning. Concurrent unpublished work [10] argues for end to end optimisation of multi stage LLM harnesses, and
M2 is essentially an instance of such a pipeline. The R4 result, where the router is wrong 0/15 times at top 1 but M1’s catch
all framing still recovers the case, is a small counterpoint suggesting that pipeline complexity does not always pay.

3    Background: The Verification Gap

end outright or hand Z3 something it cannot finish. The list that keeps showing up in CURVE 25519- DALEK and needing

 • Constant time helpers from subtle. .ct_eq, .conditional_assign, and .conditional_select cannot
   be verified by Verus through the trait impls, so DALEK - LITE calls explicit wrappers such as ct_eq_bytes32 and
   conditional_assign_u64.
 • Chained method calls. An expression such as (&a + &b).square().mul(&c) gives the prover no place to insert
   intermediate ensures, so DALEK - LITE breaks each chain into named locals.
 • Iterators and closures. .iter().map(...) becomes an indexed for loop carrying explicit loop invariants.
 • copy from slice and Default::default(). Replaced by indexed copies and explicit literals.
 • Unary negation on a reference. -(&x) trips a VIR panic, so the UFCS form Neg::neg(&x) or a named wrapper
   such as negate_field_element is used instead.
 • Compound assignment. acc += a*b becomes let prod = a*b; acc = acc + prod;.
 • Tuple struct projection. Verus cannot prove an invariant on self.0[i] through a borrow, so DALEK - LITE introduces
   a named field such as { limbs: [u64;5] }.
    None of these are hard ideas individually, yet collectively they are the reason that getting a single function ready for
verification can take hours.

4     Benchmark and Taxonomy
4.1    Pattern catalogue
We diffed every source change between CURVE 25519- DALEK and DALEK - LITE and sorted the changes into 12 categories
(Table 1), giving 133 rewrite sites across 14 files. Two patterns are excluded from the automation target. R6 (struct and
visibility tweaks) mixes line local edits with architectural moves that the line anchored framework cannot handle, and R12
(cfg gating and algorithm dispatch) is the open ended residual.
4.2    Benchmark construction
Each row holds an id, a pattern label, the upstream and dalek lite paths, the enclosing function name, the original snippet, and
the ground truth snippet. Two additional flags ride along. snippet strategy records whether the extractor grabbed the
enclosing function or fell back to a fixed radius window, and verify meaningful is true when standalone verification
actually carries signal (R1, R3, R4, R5, R7, R9). On the patterns where it does not, the proof obligation lives in surrounding
ensures clauses and the ranker falls back to compile pass plus a judge call. AST hash clustering yields 65 unique clusters
across the 107 rows, and the cluster id is stored so that NN can exclude same cluster neighbours from retrieval.
4.3    Cleaning and the residual ceiling
A first pass extracted 119 candidate rows, 12 of which were thrown out: 2 tests, 4 whose ground truth bodies were more than
half comments, and 6 whose ground truth bodies had been abbreviated to {...}. The remaining 107 rows are the headline
benchmark.
    We then audited the first 10 rows by hand (benchmarks/MANUAL REVIEW.md). Only 3 of the 10 turned out to be
cleanly evaluable: 3 were test functions that dalek lite had commented out entirely (so any candidate that emits commented
code wins by accident), 3 had ground truth slices that the extractor had pulled from the wrong impl block, and 1 was
mislabeled because the catalogue’s pattern does not actually fire on the snippet. Extrapolating from those numbers, the



                                                                    3
effective evaluable share is near 30%, and a perfect oracle on this benchmark would top out around 30% to 35% rather than
100%.
     There is a second structural issue, which is that six patterns cannot be scored by a line anchored harness at all. R6, R7,
R10, and R11 all require edits coordinated across multiple files (a struct declaration plus every field access that touches
it); R9 is a one row pattern; and R8 stretches a compound expression across a multi limb loop body. None of these fit the
function level interface. We still report numbers on them, but R1–R5 is the in scope subset (n=96).

5      Agent Architecture




Figure 2: The Agentic Verification Loop. The pipeline handles infrastructure failures (splicing, syntax, imports) via an automated retry

      Figure 3 lists the seven stages, of which a few warrant extra discussion.

Real worktree, not a sandbox. An earlier prototype used a standalone Verus sandbox with stubbed helpers, which was
fast but also incorrect: candidates that would never link inside dalek lite were still verifying against the stubs. Switching to a
real cargo verus focus run against a worktree checkout fixed that problem. The per file baselines pre warm at startup
in roughly 110 seconds for the 13 files that the benchmark touches.

Where the error text lives in the prompt. Anything that changes the cached context invalidates the Anthropic prompt
cache, so putting the per turn error text in the cache slot kills the cache after turn 1. PromptParts enforces the split, with
the SKILL going in cached context and the per turn error text going in prompt. At steady state we see 5,484 cache read
tokens per turn against between 0 and 730 cache create tokens.

Symbol aware import retry. Missing symbol is the most common infrastructure failure in which the model is doing the
right thing and the harness is the one in the way. The retry walks the worktree for each missing name, finds its defining
module, inserts a use after the last existing use, and re runs verification once more. On three production cases (R4-001,
R3-007, and R3-008) this dropped the error count from 29 down to 4 with five injected paths.

    is paid for once per case, not once per turn.
    7. Roll back. Every edit is transactional. The worktree is restored between cases.

6.2     Ranker
For verify_meaningful=True patterns the ranker is lexicographic on (verifies, compiles, equiv).                       For
verify_meaningful=False the verifies field is dropped (those patterns’ proof obligations are in surrounding
ensures, not in the function body) and the ranker uses (compiles, equiv). equiv is equivalent to gt as decided by an LLM
judge prompted with (original, candidate, ground truth).

7      Results
There are three case level metrics, all calibrated by the hand judging study in Sec. 7.7.
 • verify requires at least one K=2 attempt passing cargo verus focus on the target module.
 • near equivalent corresponds to what a maintainer would accept as a starting point for a PR. The best attempt has the
   right executable body and is at most a single mechanical fix away from ground truth (a missing ensures, a missing
   decreases, or a wrong field name). The human judgment label is EQ, EQ DIFF, or NEQ FIXABLE.
 • GT match requires exact semantic and structural equivalence to the dalek lite ground truth, spec annotations included.

7.1                     Headline
The three metrics disagree about which method wins, which is itself the headline result. On verify, NN, M1, and M2 all sit
inside a 5 pp band, with NN highest at 31.8% and M1 trailing by 2.8 pp; the per pattern ordering even flips on R2, where M1
actually has more verify passes than NN (9/29 vs. 8/29). On the near equivalent metric M1 and M2 both land at 33.6%,
comfortably ahead of NN’s 28.0%, and at the attempt level the gap is much wider (93% vs. 68%). GT match is a different
story entirely: the LLM methods collapse to raw rates of 0.9% and 1.9%, and correcting for the judge’s measured recall only
pushes the upper bound to 1.6% to 3.1%.
    The GT match gap has a precise location. We hand judged 160 LLM verify passing attempts, of which 134 are NEQ
FIXABLE rather than NEQ proper: the executable body matches ground truth and the only missing piece is the spec
annotation (a named return, the ensures clause, or the proof block). The model performs the wrapper substitution that
the SKILL asks for, but does not also write the annotation that dalek lite’s ground truth bundles with the substitution, because
the SKILL catalogue explicitly puts contract insertion outside the R1–R11 scope. Sec. 7.8 tests what happens when that
scope mismatch is removed.
7.2                     Per-pattern verify and GT-match
Table 3 breaks the headline numbers down by pattern, and a few specifics are worth pulling out. NN gets 5 of its 7 GT
matches on R2 alone while the LLM picks up zero on R2. M1’s verify pass counts match or come close to NN on every
in scope pattern, but it produces no GT matches on R1, R2, or R3 and only one on R4. R5 is a casualty of the v6 rename
correction, which broke the GT strings that the NN retrieval was pulling and none of the methods recovered.
7.3                     The repair loop
The repair loop closes most of the verify gap between LLM generation and retrieval, dropping the LLM to NN verify ratio
from roughly 3× to roughly 1.1×, while GT match does not budge. The extra verify passes that repair buys for M1 and M2
are therefore non equivalent rewrites that compile and verify but that the judge calls unequivalent, which is exactly the NEQ
FIXABLE pattern the calibration later picks up. Caching costs stay low, with roughly 80% of turn 2 and turn 3 spend going
to cache reads (around 5,484 cache read tokens per turn against essentially zero cache creates at steady state).

7.5    Router accuracy
Top 1 router accuracy across the 11 label space is 64.5% and top 2 accuracy is 77.6%. The pattern worth dwelling
on is R4, where the router scores 0/15 at top 1 and only 5/15 at top 2. The reason is that the R4 markers, namely
Default::default(), copy_from_slice, and vec!, get truncated out by the enclosing function extraction before
the router ever sees them, and the confusion matrix sends those cases to R11, R8, R10, or R3 instead. M1, which ignores the
routing entirely, still scores best on R4 (60%) anyway.
7.6    NN cluster leakage
Without same cluster exclusion, mean candidate to query similarity on a 0 to 100 token_set_ratio scale is 66.96, but
excluding same cluster matches drops it to 49.23. That 17.73 point gap (with a maximum of 88.14 on one cluster) is the
retrieval signal coming from sibling rows in the same cluster rather than from any true near neighbour structure.

7.8    Spec-aware SKILL ablation
The calibration result makes a prediction: if the SKILL is augmented to ask for the spec annotation, most NEQ FIXABLE
cases should flip to verify PASS at whole crate scope. We tested this directly.

7.9   Cross pattern analysis
R2. In v2 NN dominated R2 with 15/29 verify and 11/29 GT match. The v6 rename correction broke several of those
retrievals, dropping NN to 8/29 verify and 5/29 GT match. M1 went the other way (from 4/29 verify in v2 to 9/29 in v6)
while GT match for M1 sat at 0 in both configurations. R2 is the cleanest illustration of the LLM over enriches failure mode
under GT match.

R3. R3 is iterator and closure rewrites to indexed loops. The router gets two thirds of the R3 cases right and the
SKILL contains worked examples, yet the model keeps inventing wrapper names such as to_bytes_wrapper or
copy_from_slice_wrapper despite the SKILL listing exactly those as functions that do not exist. The dominant
failure category on R3 is missing symbol.

R5, R7–R11. R5 went from 2/5 NN verify in v2 to 0/5 across all methods in v6 because the 5 R5 rows depend on a
wrapper whose name changed in the rename correction. R7, R10, and R11 are architectural multi site edits that the enclosing
function extraction cannot capture in any version, and R9 has n=1. Taken together, roughly 14% of the rewrite population
(12 of 86 in scope sites, all of R7, R10, R11, and R9) resists per function automation in this framework, and a project level
editing surface is the right next step rather than a better prompt.

8     Discussion
Two kinds of debt: framework and prompt. R6, R7, R10, and R11 all need edits coordinated across multiple files, which
a line anchored harness cannot capture, so the next iteration of this work wants a project level editing surface. The benchmark
cleaning listed in MANUAL REVIEW.md is the other side of the same framework debt, since those fixes alone would raise
the evaluable ceiling above the current ∼30% without any model change. On the prompt side, the calibration result and the
spec aware ablation together point at a SKILL change that sits entirely on top of the framework work: a 60 line addition to
the SKILL closes most of the gap between verify and GT match, which is the highest leverage single change we have been
able to identify.

Cost. Three repair turns at the Claude Opus 4.6 rate cost a manageable amount per case, with cache reads dominating and
steady state billed input running at roughly 700 tokens per turn. Running the entire 107 case benchmark costs on the order
of a single engineer hour at human rates. The real value, beyond the cost, is determinism: rerunning a case from a fresh
worktree produces the same outcome, which is not something one can say about manual rewrites.

Threats to validity. The benchmark is small (n=107, with several patterns at n ≤ 5) and has residual extraction noise. The
GT match judge has measured precision 1.000 and recall 0.600 at 95% CI [0.39, 0.78] on the 228 hand labeled attempts, and
the corrected upper bounds in Table 2 apply this recall. Two classes of judge disagreement remain on file, namely contract
free wrapper swaps in R3-009 and alias conditional spec renames in R4-002/003/004/005 NN-0; both narrow the residual
uncertainty rather than expand it. The benchmark also contains extraction artifacts (R3-012’s GT slice, for example, points to
a different region than the Product/Sum impl the catalogue labels it with), and these are flagged in MANUAL REVIEW.md.
The infra to proof split is categorical, and compile error is bucketed as proof content even though many of those compile
errors are morally infrastructure (wrong wrapper name), so the 48% to 52% infrastructure share is a lower bound rather than
the true rate. Finally, the 10 case spec aware ablation has small n and confounds the splice strategy with the augmentation;
the 3/3 content match number is sharper but rests on three cases.

9     Conclusion
The structural rewrite step that precedes formal verification of production Rust is a real and measurable bottleneck. We
built an agent that automates this step, benchmarked it on 107 paired rewrite obligations from CURVE 25519- DALEK and
DALEK - LITE , hand calibrated the metric used to score it, and ran a small ablation that locates the dominant prompt design
gap.
    On the loose verify metric the LLM agent reaches retrieval parity on a small clustered benchmark where retrieval has a
structural advantage, while the spec aware near equivalent metric puts the LLM ahead at both the case and attempt level.
Strict GT match flips the picture: the LLM loses by a wide margin, and the 228 attempt calibration tells us exactly where the
margin sits, namely in a single missing transformation (the spec annotation). The 10 case ablation tests the obvious fix and
gets 4/10 overall and 3/3 on the clean splice subset. Beyond the model side of the picture, about half of all failures across all
methods happen inside the harness or the front end before the prover gets a chance to run.
    The artefacts left behind by this work are a 107 row paired benchmark, a 12 pattern taxonomy, a reproducible verifier in
the loop agent, a 228 attempt hand judged calibration study (precision 1.00, recall 0.60), and a spec aware SKILL prototype
with the lift data attached. In rough priority order the obvious next steps are to (a) extend the spec aware ablation to the full
∼76 case NEQ FIXABLE population, (b) build a project level editing surface to cover the multi site patterns (R6, R7, R10,
R11) that currently sit at 0%, and (c) clean the benchmark per MANUAL REVIEW.md to lift the evaluable ceiling.
