                                                     Software modernization often relies on natural-language specifications recovered
                                                     from an existing implementation. Incorrect or missing requirements can lead to
                                                     defects in the modernized system. We introduce fidelity probes to check a specifi-
                                                     cation against the code and guide its revision. Each probe pairs a question about
                                                     program behaviour with a reference answer derived from the code. A language
                                                     model answers the question using only the specification, and the fraction of agree-
                                                     ing answers defines fidelity. Disagreements flag conflicting claims or missing
                                                     information and guide proposed corrections and additions to the requirements. An
                                                     LLM generates probes directly from code or phrases facts selected through control-
                                                     flow, data-flow, and call-graph analysis. We use an observability rule to focus
                                                     probe questions on behaviour that the modernized system is intended to preserve,
                                                     including user-visible outputs, changes to stored business data, and interactions
                                                     with other systems. We revise the specification using fresh probes and evaluate
                                                     each version on a fixed held-out set. A repair–regression model describes how
                                                     new failures can offset the gains from repairs. On CardDemo, held-out fidelity
                                                     improves from 0.59 to 0.89, exceeding free-form revision from source code. We
                                                     also evaluate the method on industrial systems and public documentation, and
                                                     assess probe quality and reported defects through human reviews and comparison
                                                     with an independent requirements audit.



                                         1     Introduction
                                         Modernizing a legacy system often requires a specification of the behaviour that must be retained
                                         in the modernized system. Recovering business rules from the existing code provides a basis for
                                         redevelopment (Sneed & Verhoef, 2019), and the resulting requirements guide both implementation
                                         and acceptance testing. If these requirements misstate a business rule, the same mistake may be
                                         carried into both the modernized software and the tests used to assess it. Because the specification is
                                         written in natural language, we cannot check its agreement with the code by executing the document.
                                         Question-answering methods evaluate summaries by asking the same questions of a summary and its
                                         source, then comparing the answers (Wang et al., 2020; Scialom et al., 2021). We apply this idea to
                                         code and specifications, using answers derived from the code as the reference. Comparing these with
                                         answers drawn from the specification helps identify requirements that may need revision.
                                         We introduce fidelity probes to evaluate natural-language specifications and documentation, whether
                                         written manually or generated by an agentic pipeline. Each probe pairs a question about program
                                         behaviour with an answer derived from the code. A language model answers the question from the
                                         specification alone, and a separate model call compares its answer with the reference. We distinguish
                                         agreement, a contradiction when the document makes a conflicting claim, and a coverage gap when it
                                         provides no answer. The fraction of agreeing probes gives the fidelity score. Contradictions and gaps
                                         provide evidence for proposed edits to the requirements.

Figure 1 illustrates the setting. The code A defines a discount policy, and the candidate specification
B expresses it as EARS-style requirements with stable identifiers (Mavin et al., 2009). Consider a
probe asking which base discount applies to an order of exactly 1 000. The code gives 15%. If a
specification instead assigns 20%, the disagreement identifies a boundary error in the requirement. A
separate probe can ask how premium status affects the discount. If the document does not describe
the premium increment, the unanswered question identifies a coverage gap. The two findings lead to
different edits: correcting the threshold in the first case and adding the missing rule in the second.
Fidelity probes supply “another level of indirection” (Lampson, 2021): a question and reference
answer make a behavioural claim checkable, much as a test pairs a case with an expected result.
Questions in the application’s vocabulary let business analysts review these claims, while source ref-
erences support technical inspection. The observability rule permits abstraction: platform mechanics
matter only when they affect the behaviour in scope.
A language model revises the specification using findings from fresh probes. A fixed held-out set
and judging procedure provide a common basis for comparing documents and revisions. The reviser
never receives held-out questions or verdicts, and model parameters remain fixed.
We compare the loop with single-shot and fixed-probe variants and a free-form baseline that adapts
iterative self-refinement (Madaan et al., 2023) to revision from source code (Section 5.2). CardDemo
(Amazon Web Services, 2022) is the main benchmark, with additional studies on industrial systems
and public documentation. Our repair–regression analysis explains plateaus through the balance
between repairs and newly introduced failures (Section 4).


2    Related work

Verification and testing. Formal methods such as Dafny, Lean, and TLA+ reason about machine-
interpretable specifications (Leino, 2010; Moura & Ullrich, 2021; Lamport, 2002). Our setting in-
volves natural-language requirements produced before a replacement is implemented. Test-generation


                                                           2
methods (Claessen & Hughes, 2000; Godefroid et al., 2005; Sen et al., 2005; Pacheco et al., 2007;
Fraser & Arcuri, 2011) check behaviour by executing programs. We use questions to assess whether
the requirements describe the behaviour of the reference implementation.
Refinement and specifications. Self-Refine, Reflexion, ReAct, and Self-Debugging use feedback to
improve model outputs (Madaan et al., 2023; Shinn et al., 2023; Yao et al., 2022; Chen et al., 2024).
We adapt self-refinement to requirements as a free-form baseline and compare it with revision guided
by probe failures. Clover, Wybe, and specification synthesis methods connect code generation to
formal checks (Sun et al., 2024; Gloeckle et al., 2026; Ma et al., 2025; Wen et al., 2024; Wu et al.,
2024; Ye et al., 2026). Our target is a natural-language document, and the feedback is a sampled
agreement score with evidence for individual edits.
Grounding and evaluation. The graph channels build on program slicing and dependence analysis
(Weiser, 1984; Ferrante et al., 1987; Horwitz et al., 1990; Reps et al., 1995). We attach source
locations and requirement identifiers to findings so that reviewers can trace their evidence. Models
still phrase the questions and compare the answers, and errors can arise in either step. LLM judges
can also introduce systematic biases (Zheng et al., 2023; Wang et al., 2024; Liu et al., 2023). We
compare results across models and use human review to check the probes and the findings they
produce.

3    Fidelity probes
Let A be the reference implementation and B the candidate specification. We measure whether B
describes the behaviour of A. Intended changes to legacy behaviour must be recorded separately.
A generator returns probes Q(A) = {(qi , yi , κi )}ni=1 , with a question qi , reference answer yi ,
and behaviour category κi . Each probe also records a source location or extracted fact so that its
reference answer can be inspected. To score the probe, an LLM answers from B alone, returning
J(B, qi ) = (ŷi , ei , ci ), with an answer ŷi , a supporting passage ei in B, and a support flag ci .
This call sees neither the code nor yi . The flag is supported when the document supplies enough
information to answer, and uncertain when that information is absent or ambiguous.
Fidelity and actions. A separate comparator receives the question and both answers, then returns a
Boolean agreement decision. We write ŷi ≡ yi when it accepts the pair. Its prompt allows differences
in wording and some differences in specificity: an exact threshold and a general statement that the
limit is validated can agree (Appendix O.5). Thus an omitted detail need not cause disagreement. Let
T denote the indices of the probes being evaluated. When the comparator rejects a pair, the support
flag distinguishes a conflicting answer from missing or ambiguous information:

Definition 3.1 (Behaviourally observable probe). A fidelity probe is behaviourally observable if it
asks about business functionality that a user can observe through system outputs, changes to stored
business data, or interactions with other systems. The probe may concern an effect itself or the
business rules and conditions that determine it. Internal structures and platform mechanisms are
relevant only when they affect that functionality.
We implement this rule through fixed prompt instructions and filters on graph facts; these do not
determine which observable behaviours a particular modernization project must retain. For example,
a migration may redesign a payment interface while preserving the rules for updating balances and
accepting payments. Probes for that migration would ask how a payment changes the balance and
under which conditions it is accepted. Questions about interface behaviour depend on what the
modernized system is intended to preserve.
The informalizer uses fixed prompts and temperature zero, but its wording can still change the
meaning of a fact. The template comparison examines how phrasing affects the score, while the
human reviews assess correctness and whether the probes cover behaviour relevant to the modernized
system (Section 5.6, Appendix M).

4    Analysis of revision progress
Each revision can repair some probe failures while introducing others. We analyse these transitions
to explain how fidelity changes and why improvement can plateau. Section 5.1 measures the repair
and regression rates on a fixed held-out set and uses them to interpret the revision trajectory.
Let πk be the fraction of failing probes repaired in a revision and rk the fraction of agreeing probes
that regress, both measured on the same fixed probe set. The next score combines probes that remain
in agreement with those that move from failure to agreement:
             Fk+1 = (1 − rk )Fk + πk (1 − Fk ),               Fk+1 − Fk = πk (1 − Fk ) − rk Fk .          (4)

For πk + rk > 0, Fk† = πk /(πk + rk ) is the fidelity level where gains from repairs balance losses
from regressions. Progress is non-negative precisely when Fk ≤ Fk† . For constant rates, we write this
level as F † .
Theorem 4.1 (Constant-rate convergence). If the exact recurrence has constant rates π, r, with
π + r > 0 and |1 − π − r| < 1, then Fk − F † = (1 − π − r)k (F0 − F † ) and Fk → F † = π/(π + r).

Substituting rates measured for a completed revision reproduces its observed score. Forecasting a
later revision requires an additional assumption that the rates will remain stable. Appendix A provides
proofs and a separate analysis of sampling uncertainty.

5     Evaluation
Our main benchmark is AWS CardDemo (Amazon Web Services, 2022), a public credit-card appli-
cation. The main revision experiment covers 15 COBOL programs, about 12 k lines, with curated
EARS-style specifications averaging 127 requirements with stable identifiers per program. The pro-
grams map to eleven functional requirements documents; some share documents (Appendix G). The
main run uses the direct LLM channel, with Opus 4.6 as generator, judge, and reviser at temperature
zero. We did not repeat these comparisons across random seeds.
Additional studies use two proprietary mainframe systems, System A (COBOL, about 480 k lines
including copybooks) and System B (PL/1, about 57 k lines). We also evaluate Redis command
documentation against six C modules (about 6.7 k lines) and PetClinic specifications against 25 Java
files (about 1.8 k lines). An independent audit of System B’s requirements supplies external human
judgments.

and 911 held-out probes (Table 3). Each removes repeated revision, resampling, or probe feedback.
All perform seven revisions except the single-shot variant, which performs one. Probe-based variants
use the direct LLM channel.

Single-shot revision makes one pass using probe failures. Comparing it with fixed probes examines
further revision on the same initial curriculum. Both iterative probe-guided variants achieve higher
held-out fidelity. The free-form baseline adapts Self-Refine (Madaan et al., 2023) to specifications.
The same reviser reads the source and current specification to improve their alignment, without probe
questions, reference answers, or verdicts. Held-out probes only score its output. Probe feedback
supplies explicit discrepancies to repair; free-form revision relies on the reviser’s own assessment of
needed changes. Most of its gain occurs in the first revision, with little subsequent improvement. The
resampled loop achieves 6.8 percentage points more held-out agreement than free-form revision under
the shared judge. Section 5.6 separately assesses the accuracy of probe answers and verdicts. Fixed
probes retain the initial curriculum throughout the loop. This variant achieves the highest held-out
fidelity, but scores better on the reused curriculum at every revised checkpoint. Its mean curriculum–
test gap is 3.7 percentage points, compared with 0.1 for resampling. These means average signed,
pooled score differences over the seven revised documents, using the same available programs for both
scores at each checkpoint. Missing intermediate program evaluations limit trajectory comparisons.

5.4   Generator, judge, and reviser substitutions

This study asks whether improvement depends on the model that writes the curriculum. We replace
the generator while retaining Opus as judge and reviser, with variants spanning five model lineages
(Appendix D, Table 10). Sonnet, Qwen, and GPT-OSS improve held-out agreement; DeepSeek and
Gemma show larger differences between curriculum and held-out scores (Figure 4, left). The held-out
set comes from the original generator. A difference can therefore arise even if the replacement
generator is stable across iterations, because its questions cover different behaviour. The sweep does
not isolate overfitting or temporal drift as the cause.
To test sensitivity to the other model roles, we re-judge the same specifications using Qwen and
GPT-OSS and separately use these models for one-step revision (Figure 5). Changing the judging
model changes both the specification answerer and answer comparator. On the common 785-probe
core, pooled gains through B3 are 31.6, 25.5, and 27.3 points for Opus, Qwen, and GPT-OSS.
In separate runs with each model as reviser, fidelity after one revision is 0.871, 0.850, and 0.834,
respectively. All three revisers improve agreement. We use human review to examine errors that
agreement between models could miss.

6     Limitations

The indirection through probes relies on LLMs to phrase questions and answers and judge agreement.
Errors in these steps can distort scores and misdirect revisions, so the loop need not reach full
measured fidelity. Probes may also miss cross-file behaviour, and shared errors can persist through
resampling. Reviewers need the modernization scope to distinguish intentional interface omissions
from defects. High fidelity does not certify behavioural equivalence. We have no independent
assessment of complete revised documents. Evaluation alone used 434.8 million input tokens and
39.6 summed program-hours; revision calls are additional (Appendix H).


7     Conclusion

We contribute (i) fidelity probes that compare answers from natural-language specifications with code-
derived reference answers to questions about observable behaviour; (ii) a revision loop using fresh
direct or graph-derived probes and fixed held-out evaluation; and (iii) a repair–regression analysis
explaining how new failures can offset repairs. For human audits, the probes present questions in
business language alongside answers from code and specifications, giving domain experts specific
behavioural claims and cited evidence to examine.
On 15 CardDemo programs, seven revisions raise held-out fidelity from 0.587 to 0.885 on 911
questions, compared with 0.817 for free-form revision and 0.908 for fixed probes. Additional studies
cover industrial COBOL and PL/1 systems, PetClinic, and Redis documentation. Human reviews
identify errors in probes and revisions. Whether the revised specifications improve modernized
software remains to be evaluated.

A     Proofs and formal statements
The transition identity is an accounting result on a fixed probe set. Convergence and concentration
require additional assumptions, stated below. In particular, a lower bound on improvement does not
establish contraction or a ceiling on attainable fidelity.

A.1   One-step improvement on a fixed probe set

Assumption A.1 (Conditional repair and regression bounds). Fix a document Bk and a probe set
T . For each probe that agrees on Bk , the probability of agreement on Bk+1 is at least 1 − rk . For
each failing probe, that probability is at least πk . Probabilities are conditional on Bk , T and any fixed
judging procedure.
Theorem A.2 (Expected one-step improvement). Under Assumption A.1,
                E[F (Bk+1 ; T ) | Bk , T ] ≥ (1 − rk )F (Bk ; T ) + πk (1 − F (Bk ; T )).              (5)
For πk + rk > 0, expected progress on T is non-negative if F (Bk ; T ) ≤ πk /(πk + rk ).

Proof. Partition T into agreeing and failing probes on Bk . Apply the respective probability bound to
each indicator of agreement on Bk+1 , sum the bounds, and divide by |T |. Independence between
probes is unnecessary for this linearity argument. The progress condition follows by subtracting
F (Bk ; T ).

Corollary A.3 (Deviation lower bound). Let Fk† = πk /(πk + rk ) when the denominator is positive.
The preceding result gives
                  E[F (Bk+1 ; T ) | Bk , T ] − Fk† ≥ (1 − πk − rk )(F (Bk ; T ) − Fk† ).               (6)

Proof. Subtract Fk† and use πk = (πk + rk )Fk† .

This is a lower bound, not a bound on the absolute deviation. It does not prove convergence. It also
concerns the same T on both versions, not a new curriculum sampled after revision.

A.2   Exact transition recurrence

On a fixed probe set, define πk and rk as the observed conditional transition fractions. Counting the
retained agreements and repaired failures gives Eq. 4 exactly. If either starting class is empty, its
conditional rate is undefined, but its contribution to the count is zero.
Theorem A.4 (Convergence with constant rates). For the exact recurrence with constant π, r,
π + r > 0, and |1 − π − r| < 1, the sequence converges to F † = π/(π + r).

Proof. Subtract the fixed-point equation F † = (1 − π − r)F † + π. This gives Fk+1 − F † =
(1 − π − r)(Fk − F † ). Iteration gives Theorem 4.1; the multiplier’s absolute value is below one, so
the deviation tends to zero.

The same conclusion holds for an exact variable-rate recurrence if the rates converge and |1 − πk −
rk | ≤ ρ < 1 eventually, with a positive limiting sum. To see this, subtract the limiting fixed point
to obtain |ek+1 | ≤ ρ|ek | + ηk , where ηk → 0. For any ϵ > 0, choose a late enough index that
ηk ≤ (1 − ρ)ϵ. Iteration then gives lim supk |ek | ≤ ϵ, and letting ϵ → 0 proves convergence. The
measured rates are not constant, so fitting this recurrence to an observed transition is an explanation
of that transition, not an independent prediction.

A.3   Finite-sample concentration

Assumption A.5 (Independent evaluation samples). At a fixed checkpoint, Bk is independent of
the evaluation probes. The test bank consists of ntest i.i.d. draws from a fixed distribution. For
a curriculum–test bound, the curriculum must also consist of ntrain independent draws from that
distribution, independent of Bk . The judging procedure is fixed, or its randomness is included in the
independent draws. Let µk be the resulting population agreement probability.

K     Channel construction and emitted fact types
Construction. The static-analysis pipeline expands copybooks, parses each program, and builds
the graphs used for extraction. The annotated control-flow graph (ACFG) has decision and action
nodes. Actions carry read and write sets, and each decision has a resolved true-branch successor.
The data-flow graph (DFG) records def-use chains. The extractor uses these chains to compute
backward slices from observable sinks: screen output, persisted business records, and cross-system
messages. The system-dependence graph (SDG) combines control dependence, data dependence,
and interprocedural analysis.
The CallGraph channel selects only the interprocedural CALL, XCTL, and LINK edges from the SDG.
For dynamic calls, the extractor scans the call site for a table-indexed or context-variable program
name and tags the target as dynamic. This resolution is lexical; the extractor does not use data-flow
analysis to resolve the target.
Emitted fact types. The extractor tags each fact with one type, and a single function maps that type to
one channel. Table 16 lists the types that the pipeline emits. The emitted record types form a disjoint
partition. Facts assigned to different channels can still describe overlapping program behaviour.

Sampling. Within a channel, the sampler shuffles candidate facts and selects without replacement,
drawing at most one probe per SDG region (a paragraph for intraprogram facts, a call site for
interprogram facts) per iteration. This limits clustering within a paragraph.
Before sampling, the observability filter excludes facts whose answers depend on platform details such
as file-access ordering, queue operations, buffers, paragraph identifiers, or record layouts. Persisted
business data remains in scope: updating an account balance is observable business behaviour, while
the storage mechanism used for that update is not.

L     Manual evaluation: protocol and results
Five human checks address different questions: a source audit examines reference answers, verdicts,
and edits; a blind review checks paired-probe equivalence; an external audit supplies requirement-
level defect labels; and two later expert panels assess probe relevance and reported findings. The later
panels use additional CardDemo runs and do not re-evaluate the main revision trajectory.
Check 1: expert audit of probes, verdicts, and edits. We fixed the sample before annotation,
drawing 120 held-out CardDemo probes with seed 29844. Stratification used the final-document
verdicts: 100 agree, 10 contradict, and 10 gap, with every nonempty program-by-verdict cell
represented. We also sampled 30 applied edits: 20 additions, 7 fixes, and 3 removals. For each
probe, the expert assessed the reference answer against the COBOL source and judged whether the
model’s verdicts at iteration 0 and the final iteration were correct. For each edit, the expert assessed
faithfulness to the code and whether an incorrect claim had been introduced.
The expert worked from line-numbered source and specification excerpts, without access to the
pipeline. The pack showed the recorded model verdicts and contained AI-drafted judgments that the


                                                      26
expert could confirm or override. This was AI-assisted human adjudication. The expert changed the
draft judgment on 25 of the 120 iteration-0 verdict cells, 7 of the 120 final-iteration cells, 0 of the 120
reference-answer cells, and 3 of the 60 edit cells (two judgments per edit). Every change included a
rationale identifying the label the expert considered correct.
The expert confirmed 119 of 120 reference answers; the remaining answer named a prompt that the
calling path cannot reach. Verdicts were correct on 93 of 120 initial-document evaluations and 109 of
120 final-document evaluations. Across revisions, 23 verdicts moved from wrong to right and seven
the other way. Of the 30 edits, 25 were faithful and introduced no incorrect claim. The remaining five
introduced an incorrect claim, including four that mixed correct and incorrect additions.
Check 2: equivalence re-check. A second reviewer assessed 53 pairs of informalized probes with
the comparator’s verdicts hidden: all 3 pairs it called different and 50 it judged equivalent. The
reviewer assessed question equivalence and answer equivalence separately. Agreement with the
comparator was 51 of 53 (Appendix C). This reviewer did not participate in the source audit.
Check 3: independent requirements audit. Professional analysts engaged by the owner of System
B reviewed the derived requirements using their own protocol, with no contact with our work. They
flagged 72 of 396 requirements as defective: 20 as wrong and 52 as partial. We compared their
findings with the requirements cited by failing probes. At the level of program-scoped requirement
instances, 43 of 872 instances were in the flagged set. Failing probes cited 33 of these 43 instances
(77 percent), compared with 374 of the 829 unflagged instances (45 percent). The odds ratio was 4.0,
with Fisher exact p = 0.0001.
Within the matched audit subset, 23 of 28 incomplete requirements were cited by a probe with a
gap verdict. The association between the auditors’ “wrong” label and our contradiction verdicts was
positive (4 of 11 matched wrong requirements, 36 percent, against a 20 percent base rate), but not
significant at this sample size (p = 0.25). The audit was not exhaustive, so an unflagged requirement
is not necessarily correct and the unflagged rate cannot be interpreted as a false-positive rate. The
comparison uses different units: auditors judged individual requirement statements, whereas probes
were answered from program-specific documents. A later inspection found that document assembly
omitted some requirement blocks in 18 of the 21 judged programs, retaining 64.9 percent of the
available text by character count. The reported association therefore concerns these incomplete
excerpts; its strength on complete documents has not been measured.
Check 4: probe-quality panel. Three mainframe modernization specialists reviewed 24 generated
probes from a later CardDemo run using Claude Opus 5 as generator and judge. Eight probes were

206 requirement-derived questions.
Each reviewer saw the question, its code-derived answer, and cited source lines. They classified the
question as business behaviour, technical noise, or unclear, and could flag an incorrect answer. One

gave a binary decision, 16 were unanimous, raw pairwise agreement was 0.895, and Fleiss κ = 0.77.
Treating unclear as a third category gives κ = 0.64 on 22 questions. Across all 24 questions, the
majority classified 14 as business behaviour and eight as noise, with one unclear judgment and one

A rubric rater (Opus 5) separately classified each question and answer without reading source code.
It agreed with 20 of 21 independent, decided majority judgments (Cohen’s κ = 0.89). Including the

The rater repeated its label on 23 of 24 questions across five reruns. The one decided disagreement
concerned whether a menu’s accepted option range should survive a change of user interface.
Reviewers flagged six answers as wrong. A separate model-based code review rejected those six

M      Template against LLM informalization

Design. We generated two versions of each probe from the same 90 CFG guard facts. Each fact
contains a guard condition G and its true-branch action T , extracted deterministically from the
annotated control-flow graph. Claude Opus 4.6 judged both versions against the corresponding
program’s initial specification B0 . The template version inserts the fact fields verbatim into the
question “Under what condition does the following occur: T ?” and the reference answer “This
occurs when G.” This step uses no LLM. The LLM version uses the frozen informalizations from the
stability check in Appendix C. The 90 facts span 19 programs. They come from the 100-fact stability
sample, excluding ten facts whose identifiers collided across programs or whose program had no B0
mapping.
For example, a template asks when MOVE ’Y’ TO WS-ERR-FLG occurs, whereas the corresponding
informalized question asks what happens when a processing date is blank. Both refer to the same
extracted guard, but their wording asks the specification to recover different information.
Results. Fidelity is 22.2 percent (20 of 90) for the template arm and 44.4 percent (40 of 90) for the
informalizer. Coverage gaps account for 61 versus 37 probes, and contradictions for nine versus
thirteen.
Thirteen facts pass in both arms and 43 fail in both. The template fails where the informalizer passes
on 27 facts, and the reverse occurs on seven (exact two-sided McNemar p = 0.00082). A scanner for
COBOL identifiers, CICS attention keys, analysis-helper names, and the extractor’s banned platform
terms flags all 90 template probes and no informalized probes.
Interpretation. Templates preserve source identifiers that are absent from business requirements,
which can make an otherwise relevant rule harder to locate. The question pair may also change
direction: asking which condition causes an action is different from asking what follows from a
condition. The informalizer can add or omit context. The paired agreement difference therefore
measures sensitivity to rendering; it does not show that every higher-scoring informalization preserves
the original fact.
