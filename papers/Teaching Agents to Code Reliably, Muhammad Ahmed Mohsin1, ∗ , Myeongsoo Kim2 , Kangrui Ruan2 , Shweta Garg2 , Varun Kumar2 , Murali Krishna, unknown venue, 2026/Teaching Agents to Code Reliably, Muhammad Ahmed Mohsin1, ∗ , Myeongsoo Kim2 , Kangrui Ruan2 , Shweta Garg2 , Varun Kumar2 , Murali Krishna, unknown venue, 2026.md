                                        1    Introduction

                                        Autonomous coding agents resolve repository issues through code inspection, editing, and test execution (Jimenez et al.,
                                        2024; Yang et al., 2024). Repeated attempts and verification can improve resolution by increasing inference-time computation
                                        (Brown et al., 2024; Snell et al., 2024; Han et al., 2026). Their benefit depends on whether additional attempts produce correct
                                        repairs and whether the agent can identify them. Attempts can revisit the same edit location or repeat an incorrect repair. A
                                        test generated by the agent can share the patch’s mistaken interpretation of the issue and accept incorrect behavior (Ahmed
                                        et al., 2025). More candidates do not guarantee a correct selected patch.
                                            We distinguish candidate coverage from selection quality. Coverage is the fraction of issues for which the candidate
                                        set contains at least one correct repair. Selection quality is the fraction of those issues for which the agent returns a correct
                                        candidate. Oracle pass@8 measures coverage across eight attempts, whereas the accuracy of the selected patch depends
                                        on both quantities. Verification also guides the search by determining whether the agent revises a patch, explores another
                                        location, or stops. The verifier therefore affects both the candidates generated and the patch returned.
                                            We hypothesize that training can improve repair search and test discrimination under a fixed backbone and scaffold. Our
                                        diagnostic study examines edit locations, repair approaches, and verification decisions on SWE-bench Verified. Repeated self-
                                        verification produces few changes to the submitted patches, while different problem-solving preambles produce complementary
                                        repairs. Proactive localization visits more locations than reactive search but resolves fewer issues (Section 2.1). These
                                        observations motivate training the agent to use execution feedback when choosing its next edit and to evaluate tests by their
                                        ability to detect incorrect repairs. Execution provides evidence beyond the agent’s judgment of its own output (Huang et al.,
                                        2024).
                                           Our approach combines a test-time diagnostic with two training stages. The diagnostic pairs exploration of edit locations
                                        and repair approaches with differential verification, which runs a reproduction on the patched and reverted repository.

2     Methodology

This section describes the test-time search procedures, weighted trajectory supervision, and reinforcement learning objective.
Figure 1 illustrates exploration and verification within one repair trajectory.


2.1    Test-Time Scaling Methods on Coding Agents

The diagnostic uses all 500 SWE-bench Verified issues to analyze repair and verification failures. We select 230 issues from
this population for training dataset curation and hold the remaining 270 out of SFT and RL training. All search procedures
run on the same backbone and scaffold. Table 1 reports resolution, agent-steps, attempts per instance, and diversity. Attempt
limits and stopping rules differ by procedure, so each comparison reflects an accuracy and cost trade-off.
    We compare single attempts, repeated self-verification, eight repair preambles, proactive localization, and reactive bans on
failed edits or locations. The preambles reach an oracle union of 305/500 issues, while repeated self-verification leaves 78 to
85% of audit passes without a code change. Appendix A.1 describes the procedures and scoring rules.
   Differential-verification search pairs up to eight locations and repair approaches. It runs each reproduction on the patched
and reverted trees, checks repository tests and changed-line execution, and uses the resulting score to stop or prune search.
A reproduction that passes on both trees receives zero credit. Search uses repository execution rather than hidden grader
feedback. It resolves 52.8% of issues against 46.8% for the eight-sample control, using 48.1% of its agent-steps (Table 1).
Appendix B.11 reports component ablations.


2.2    Supervised Fine-Tuning on Weighted Agent Trajectories

We train the policy to imitate repair trajectories weighted by outcome quality, exploration, and agent-step count. The training
interface matches the inference interface. Some examples rely on verifier outcomes rather than gold labels, so the corpus can
contain incorrect repairs.


Corpus construction. We curate the SFT corpus from the 230 issues selected after the all-500 failure analysis in Section 2.1.
Trajectories from the remaining 270 issues are excluded from SFT and RL training. The corpus includes the six search
procedures in Table 1 and the methodology-diversity runs, generated with Qwen3-Coder-30B-A3B-Instruct under mini-SWE-
agent. Each example records the conversation, final patch, edit locations, agent-step count, verifier outcome, available gold
label, and behavior tags. Trajectories are ranked within each instance id by the weight defined below, with ties resolved
by fewer steps. The retained corpus contains 5,061 examples from 230 issues.
    The corpus includes contrastive-edit examples pairing a correct repair with an incorrect candidate at the same location,
and reproduction examples distinguishing buggy from fixed behavior. Contrastive examples receive additional weight when
the incorrect candidate passed the verifier. These examples are included in the 5,061 total.


Quality tiers. Each example receives the weight of the first tier it matches. Tier T 1 has weight 1.0 and requires a gold-
resolved patch that was selected or received a verifier score of at least 1.0. Tier T 2 has weight 0.6 and requires either a verifier
score of at least 1.0 or a gold-resolved patch with a verifier pass. Tier T 3 has weight 0.25 and requires a non-empty patch
with a weaker positive verifier signal. All remaining examples receive weight 0. Only T 1 requires a gold label.

2.3    Reinforcement Learning for Discriminative Verification

The SFT objective imitates trajectories without ever rewarding a test for rejecting an incorrect repair (Shum et al., 2025). We
add a reinforcement objective that evaluates generated tests against incorrect programs, which measures which incorrect
behaviors a test detects.


                                                                             3
Generated objects. For each training issue, the policy produces a patch P and a test T containing assertions {a1 , . . . , an }.
We draw k rollouts per issue. The other k − 1 patches in the group are sibling repairs, which provide additional candidates for
test evaluation. A gold execution oracle G determines whether a patch satisfies the training issue’s evaluation tests.


Oracle access and rollout feedback. The policy observes repository files, command results, and the pytest output of T
on P . Revision rounds return surviving patch variants as counterexamples that the policy can use to revise its patch or test.
The policy does not receive gold tests, gold verdicts, assertion-credit scores, or group advantages. Oracle labels are used by
the scoring procedure described below. The completed rollout receives a scalar reward, from which we compute trajectory
and assertion-token advantages for the training update.


Mutation evaluation. The harness generates variants from the current patch using deterministic operators and a frozen
model distinct from the policy. The operators cover boundary, value, logic, control-flow, and effect faults. Model-generated
variants are produced during the run rather than retrieved from a cache. A line trace checks that the test executes the patched
lines. A variant counts as detected when an assertion fails. Uncaught errors receive no detection credit.
    The scoring set S contains oracle-rejected variants and oracle-rejected sibling repairs. Candidates that pass the gold tests
are excluded from this negative set. Passing the gold tests does not establish semantic equivalence, but it prevents those
candidates from being scored as known incorrect repairs. We record the detected subset as Kill(T ). Appendix A.6 gives a
worked example.
   The repair loop allows up to three revision rounds and applies a penalty for additional rounds. Exploration terms measure
group diversity across edited files and assertion targets, coverage of fault classes, and repetition of test templates. These terms
supplement the patch-correctness and test-discrimination signals.

3     Evaluation

3.1    Evaluation Protocol

Populations and exposure. Section 2.1 analyzes all 500 SWE-bench Verified issues. We curate SFT and RL data from 230
of them and evaluate the trained policies on the remaining 270, of which 180 come from training repositories and 90 from
repositories excluded from training. Held-out means excluded from SFT and RL training. All 270 appeared in the diagnostic,
so this split measures held-out issues within a benchmark used for method development rather than an out-of-distribution
evaluation. Transfer uses DeepSWE (113 tasks), SWE-PolyBench, SWE-bench Lite, and SWE-bench Pro (731 issues). The
30B study evaluates all four after SFT and all but Lite after RL, while the 7B and 14B runs also evaluate Lite (Appendix A.8).



Decoding and aggregation. The policies share the backbone, scaffold, tools, context limits, and attempt budget. Pass@1
uses the greedy first attempt, and eight-attempt evaluation adds seven samples at T = 0.7, so the samples are not identically
distributed. This budget differs from the eight methodology-conditioned chains and the candidate grid of Section 2.1. The
configuration specifies three seeds.


Candidate populations and metrics. Coverage and selection use each policy’s own eight-candidate sets. Verifier dis-
crimination instead uses one frozen bank of labeled repairs per held-out issue, shared across policies, combining natural
incorrect repairs from several generators with correct alternatives, with labels withheld from the test-generating policy.
Cross-error-source evaluation separates familiar operators, held-out operators, an excluded semantic-mutant generator, and
natural incorrect repairs. Repair correctness is defined by the benchmark grader, so resolution and verifier labels measure
agreement with its tests rather than semantic correctness. Pass@8 is oracle coverage, Selected@8 is the fraction whose
selected candidate is correct, and selection efficiency is Selected@8/pass@8. Taking a correct repair as the positive class,
precision is T P/(T P + F P ), the false-positive rate is F P/(F P + T N ), correct acceptance is T P/(T P + F N ), and balanced
accuracy averages correct acceptance and incorrect rejection. DeepSWE verifier labels use fail-to-pass satisfaction. We report
ηk = Ukloc /k as location diversity per attempt, and agent-steps count agent interactions rather than tokens or execution time.
Appendix B.9 defines acceptance coverage, correct-alternative acceptance, and the zero-survivor audit.

(Table 5). Applying the same RL objective to the base policy yields 35.9% (Table 7), so the objective gains 4.0 points from
the base policy and 7.8 from the supervised one.

SFT increases oracle pass@8 from 46.7% to 51.1%, while RL raises it to 60.7%. Selected@8 increases from 33.5% to
38.5% after SFT and to 50.5% after RL. Selection efficiency rises from 0.72 to 0.75 and then to 0.83 (Table 3). The gains
therefore involve both the availability of correct repairs and the fraction selected by the verifier. The coverage half traces
to the exploratory behavior the corpus weighting teaches. Trained to spread attempts across locations and vary the edit, the
policy reaches 1.98 distinct localizations per issue against 1.41 for the base model, and the share of samples contributing a
new fault location rises from 0.18 to 0.25 at eight attempts, so more of the budget lands on ground no earlier sample covered.


Behavioral changes under supervision. Supervision raises pass@1 on every suite that resolves any task, by 3.3 points
on Verified and 3.8, 8.4, and 13.4 on SWE-PolyBench, Lite, and Pro (Table 2). The trajectory measures move in the same
direction on every suite, with more files read before the first edit, smaller patches, fewer test-file edits, and fewer steps to first
submission. Reproduce-first is the one measure where base leads, 94.4% against 92.1% on Verified, while rising on all four
transfer suites. This is the behavior the weighting targets. A policy that commits to one site keeps editing it, so a wrong first
localization is unrecoverable, and Section 2.1 showed that breadth alone loses to blind retry. The weighting rewards moving
on once execution rules a site out, so the added breadth lands where feedback directs it rather than across arbitrary sites. At
matched corpus and budget, removing the exploration factor lowers distinct localizations from 1.98 to 1.74 and pass@1 from
35.2% to 34.8% on Verified, and from 4.13 to 3.70 and 24.2% to 23.2% on SWE-PolyBench (Table B.10). Staging the terms
raises localization and resolution together, from 1.55 and 33.7% under uniform weighting to 1.90 and 34.8% with exploration,
while an interface-compliance control reaches 1.45 and 32.6%, below uniform on both (Table 19). Which trajectory measure
carries the effect is not separated.
    Steps to first submission decrease from 62.5 to 56.0 (Table 2), and η8 rises from 0.34 to 0.61 on DeepSWE. Location
diversity does not measure candidate correctness, so it complements rather than replaces the coverage analysis.

3.5     Reward Controls

The RL controls start from one SFT checkpoint and match training issues, update counts, and rollout budgets. Correctness-only
GRPO reaches 39.6% pass@1 and 28.5% verifier precision. Adding scalar verification reward raises these values to 40.7%
and 38.4%. Assertion credit raises them to 43.0% and 41.7% (Table 5b). Both the verification reward and assertion credit
contribute to the reported gain.
    Uniform assertion credit yields 38.0% precision and shuffling it at matched total mass yields 31.5%, so placement affects
discrimination beyond the amount assigned. Removing mutation evaluation reduces pass@1 from 43.0% to 38.1%, the largest
reduction among the component removals in Table 8. Allowing uncaught errors to count as detections reduces it to 39.6%.
These removals measure contributions within the full configuration and need not have additive effects. Ungating the shaping
terms costs 1.9 points, removing the repair loop costs 3.0 while leaving precision at 40.1%, and removing the exploration
terms costs 1.5 (Table 8).
   Group size raises both metrics, from 41.5% pass@1 and 39.0% precision at k=4 to 43.0% and 41.7% at the trained k=6
and 43.3% and 42.6% at k=16. Lowering the correctness weight raises precision to 43.2% while pass@1 falls to 38.9%
(Table 10), so the two respond differently to the same reward change.

3.6    Transfer and Limitations

RL improves pass@1 over SFT by 8.3 percentage points on train-exposed issues, 7.7 on test issues from training repositories,
and 7.8 on repositories excluded from training, reaching 45.7%, 44.4%, and 40.0% respectively (Table 5a). The gain is
near-constant across the exposure gradient while the absolute level falls, the pattern expected if the objective transfers rather
than recalling training fixes. On SWE-PolyBench, pass@1 increases from 24.2% to 31.8%. On SWE-bench Pro, it increases
from 15.7% to 20.2% (Table 6). These evaluations support transfer beyond the training issues. They do not exclude pretraining
exposure to public repositories.
    DeepSWE full resolution remains zero at this model scale, but its internal measures improve. SFT raises the tasks with
at least one satisfied fail-to-pass test from 17 to 21 of 113 and the mean best-of-eight satisfied fraction from 4.0% to 4.8%
(Table 13), which is partial test satisfaction rather than completed repair. Verifier precision uses a different positive criterion
here (Section 3.1).
    The signed assertion-credit ablation raises correct-alternative acceptance from 78.0% to 84.0%, cross-generator discrimi-
nation from 74.0% to 78.0%, and pass@1 from 43.0% to 43.3% (Table 18). This result supports adding an assertion-level
penalty for false rejection. The main results use unsigned credit, so the signed variant’s gains apply to this ablation.
    Verification remains sensitive to the source of incorrect repairs. The RL verifier rejects 91.0% of familiar-operator mutants,
84.0% of held-out operators, 79.0% of variants from an excluded generator, and 74.0% of natural incorrect repairs from
independent generators. The latter exceeds SFT by 12 percentage points, while correct-alternative acceptance remains 78.0%
(Table 16). Complete detection of a finite mutant set does not establish correctness outside that set.
    The 7B and 14B experiments gain from both stages. Verified pass@8 rises 21.9 → 30.4 → 33.3% at 7B and 27.0 →
36.7 → 42.6% at 14B, and SWE-PolyBench rises 8.0 → 17.8% and 19.8 → 37.4% (Table 14). Published coder results in
Appendix A.5 provide context but use different scaffolds, subsets, or selection protocols. They do not constitute matched
comparisons. Agent-step savings also exclude differences in token lengths and test-execution costs.

4     Related Work

Repository search and feedback. SWE-agent and OpenHands provide interfaces for repository inspection, editing, and
execution (Yang et al., 2024; Wang et al., 2024). Agentless organizes repair around localization (Xia et al., 2024), and
inference-time scaling studies examine additional attempts (Brown et al., 2024; Snell et al., 2024). Our diagnostic holds
backbone and scaffold fixed and compares how location search and verification affect repair. Generated tests also support
candidate selection (Chen et al., 2023), and we measure candidate coverage and selected accuracy as distinct outcomes.


Training repair and test generation. CodeRL trains code generation from execution feedback (Le et al., 2022), SWE-Gym
studies training repository agents and verifiers (Pan et al., 2024), and CURE co-trains a coder and unit tester with reinforcement
learning (Wang et al., 2025b). Our policy generates both the patch and its test, and the reward combines patch correctness
with detection of oracle-rejected variants. SWT-Bench evaluates tests for repository bug fixes (Mündler et al., 2024), a related
setting for assessing tests beyond whether they execute.


Mutation rewards and credit assignment. MIST-RL rewards each test for detecting mutants earlier tests missed and
penalizes redundancy (Zhu et al., 2026). Ockhamareto is the closest comparator for our token-level credit, mapping mutation
contributions to test-block tokens under a Pareto gate on suite effectiveness and size (Huang et al., 2026). Our credit
divides each detected mutant’s weight among its detecting assertions and applies a positive-advantage bonus gated by repair
correctness or complete detection, with the trajectory reward prioritizing repair correctness. These differences concern the
reward and credit rule rather than introducing mutation testing or token-level attribution.


Test and patch revision. CoHarden generates a reproduction before editing and uses mutant-based feedback to revise tests
and fixes (Tan et al., 2026), the closest comparison to our revision loop. We also train the policy from those signals and
evaluate the resulting verifier on frozen candidates, correct alternatives, and incorrect repairs from independent generators.



5     Conclusion

We hypothesized that reliable repair rests on three learnable behaviors, locating the fault, varying the edit, and verifying which
candidate to return. The first two determine candidate coverage and the third selection quality, neither compensating for the
other, and the swap estimates their contributions as additive. Weighted supervision and mutation-based reinforcement learning
improve both, with gains on SWE-bench Pro and SWE-PolyBench and, on DeepSWE, partial credit without full resolution.
The constraint is general, since a proposer scoring its own work cannot be wrong, so negatives must be manufactured rather
than collected.
    Where the verifier is weakest indicates what to improve. Rejection falls from 91.0% on familiar operators to 74.0% on
repairs from independent generators, so a wider negative distribution during training is the first direction. The second is the
signed credit rule, which charges an assertion for rejecting a correct alternative and raises correct-alternative acceptance from
78.0% to 84.0% in our ablation, though not yet under the full evaluation. Folding the verifier into the search loop, so that it
steers exploration rather than filtering afterwards, would reach the coverage limit selection cannot.

A.1    Test-time search procedures

Self-verification. The agent submits a patch, then runs up to three audit passes that read the repository, run tests, and revise,
with no grader feedback (prompt in Appendix B.12). It resolves 184/500 (36.8%) at 189,371 agent-steps (1,029 per solve),
yet 78 to 85% of audit passes change no code and across four attempts it reaches only 1.10 distinct locations and 1.31 distinct
edits. It neither escapes its wrong first guess nor stops paying to re-examine it, taking both the lowest accuracy and the highest
cost.
    Single-axis diagnosis. One attempt per issue, no retry and no diversity mechanism, fixing the single-sample reference the
other procedures answer to. It resolves 189/500 (37.8%) at 41,332 agent-steps, the cheapest run in the study at 219 steps per
solve.
    Methodology diversity. Running each issue under eight problem-solving preambles (Appendix B.13) solves overlapping
but distinct subsets, with combined oracle coverage 305/500 (61.0%), above any single preamble. This label-using union
is not a deployable rule, yet it marks the headroom. The agent already produces a correct fix for far more issues than one
strategy surfaces, so selection limits performance more than generation.
    Directed exploration. Up-front localization pins one attempt to each of 2.46 ranked sites yet resolves only 210/500
(42.0%), below blind retries (213/500), so broad coverage alone does not help. Spending attempts on the right sites does, and
that needs execution feedback. Banning a confirmed-wrong edit signature and stopping on a strong positive resolves 217/500
(43.4%) at 131,417 steps, reaching 1.84 locations and 2.79 edits with early stops on 65 issues.
    Reactive location diversity. Banning the whole location, its files and functions, resolves 225/500 (45.0%) at 585 steps
per solve, under the ban and early-stop rules of Appendix B.14. Location diversity pays only when earned reactively, and
reactive location-banning (225) exceeds reactive edit-banning (217), blind retries (213), and proactive site-planning (210), in
that order.
    Differential-verification search. The combined procedure builds up to eight candidate cells, each pairing one localization
with one repair approach. It scores every candidate by executing the agent’s own reproduction twice, once on the tree carrying
the patch and once on that same tree with the patch reverted. A failure on the reverted tree together with a pass on the
patched tree shows the patch changed the behavior the reproduction measures, which is weaker than showing the patch correct
elsewhere. The score itself rises with how much independent evidence stands behind that verdict, and it decides whether
search continues. A confirmed differential scores 1.2 when two further checks agree, the repository’s existing tests still pass
and the reproduction touches the changed lines, and 1.0 when either is missing, which reads a regression failure as pre-existing
rather than caused by the patch. A patch whose reproduction passes while the reverted run returns no verdict scores 0.3, since
the pass is real but nothing corroborates it. No usable signal or a broken harness scores 0. A vacuous differential, where
the reproduction passes on both trees, means it never exercised the fault, so the candidate takes a hard 0 and the location is
pruned. Any score of at least 1.0 is strong enough to stop the search. Every decision uses the agent’s own reproduction and
the repository tests, never the hidden grader.
    Differential-verification search resolves 264/500 (52.8%) against 234/500 (46.8%) for the eight-sample control, at 132,697
agent-steps, 48.1% of the control’s 275,943, and 3.12 attempts per issue. That is 503 steps per solve against 1,179. Early
stopping fires on about 102 issues and pruning drops 126 localizations across 73 issues, so the gains come from spending
compute where feedback says it will pay. A component ablation (Appendix B.11) isolates each part. Dropping the two-tree
differential does the most damage (52.8 → 47.4%, near the eight-sample baseline), while early stopping costs compute alone
(steps/solve 503 → 728 at unchanged resolution).

A.4     RL objective implementation details and boundary cases

Two implementation notes accompany the per-assertion credit of Eq. 4. Mapping st = ci onto every token of assertion i scales
its total bonus by the span length Li , so a per-token form st = ci /Li removes this length effect. And ordinary execution halts
a test at its first failing assertion, so reconstructing the full matrix K needs isolated, independently executable test nodes. The
Shapley reading of c̃i carries no convergence claim.
    We define the scored quantities only when their inputs exist and fix the empty cases explicitly. With no valid negatives
(|S| = 0) the kill fraction is undefined and the fixpoint bonus does not fire, so we record insufficient negatives and give no
verifier credit. With no assertions or no detected mutants we zero the local credit ci and log the event. Infrastructure or import
errors count as invalid execution and earn no behavioral-kill credit, so a broken harness earns no reward. The honesty term
penalizes a test that fails on a correct repair, so an always-failing test cannot look discriminative. We report and control the
valid mutant count and duplicate rate, since zero-survivor rates are otherwise incomparable. The gate G is an OR, so the local
bonus can fire on a resolved or complete rollout, correctness still enters only through C ORRECT, and we never read a full kill
as correctness assurance.

   an upstream model-field module (fields/ init .py). The edit term credits both a plausible or validated location
   and an edit distinct from the group, so the objective rewards covering the space and staying diverse.

B.2    Generator and verifier swap

This experiment separates the two things training changed. Repair generation and candidate selection are held in fixed roles,
and each is swapped independently between the base and trained policies, so the four cells of Table 15 span every combination
at one attempt budget. Holding the generator at base and replacing only the verifier raises end-to-end resolution from 31.9%

which patches exist. Holding the verifier at base and replacing only the generator reaches 38.5%, so both roles contribute on
their own. The interaction term is the diagonal contrast, (43.0 − 38.5) − (36.5 − 31.9) = −0.1 points with a 95% interval of

B.3    Cross-error-source transfer

A verifier trained against one family of incorrect programs may only have learned that family. Table 16 moves the error source
progressively away from training while holding the evaluation bank and the issues fixed, so any decline isolates distribution
shift in the negatives rather than a change in difficulty. Rejection falls monotonically for every policy, and for the RL verifier
it runs 91.0% on familiar operators, 84.0% on held-out operators, 79.0% on variants from an excluded generator, and 74.0%
on natural incorrect repairs written by independent systems. The decline is gradual rather than a collapse, and the margin over

outlives its training operators. The last row is the one that matters for deployment, since those repairs were produced the way
a real candidate would be, and correct-alternative acceptance holds at 78.0% there, so the verifier is not buying rejection by

B.12     Self-Verification Hook

After the agent submits a candidate patch, we inject the prompt below to run an adversarial audit over the agent’s own patch,
applied up to three times per chain and lightly edited here for space.

    Self-Verification Hook
  You have submitted a candidate fix. Assume it is wrong until you prove otherwise. For this pass you are a hostile, meticulous
  reviewer of your own work, and your only job is to find a concrete reason the patch fails. A pass that concludes the patch is fine is
  acceptable only after you have genuinely tried to break it from several angles and failed. The single most common way a wrong
  patch survives review is to read the expected answer off what the current code returns, so never do that. Re-establish what correct
  means from the issue’s stated requirement alone.
  1. Re-establish ground truth from the requirement. Restate the issue in your own words, naming the exact inputs, the exact
      expected outputs, and the conditions under which each applies. For the failing scenario, derive the correct result directly from
      the issue text before you look again at what your patch produces. List the source functions the requirement implicates. If your
      change touches none of them, you almost certainly fixed the wrong place and should relocate before going further.
  2. Re-audit for root cause. Re-read every region you edited with fresh eyes. For each edit, ask whether it removes the underlying
     cause or only masks a downstream symptom. Swallowing an exception, clamping a value into range, and special-casing the
     issue’s literal input are all symptom fixes, and you must reject them. Trace the data and control flow by hand, confirm the fix
     holds for the whole class of inputs the requirement covers, not the reported one alone, and confirm it leaves previously correct
     inputs unchanged.
  3. Test adversarially. Run the issue’s FAIL TO PASS tests first, then go past them. Write a throwaway script that constructs the
     expected result you derived in step 1 and asserts your code matches it, independent of the shipped tests. Run the repository’s
     existing tests for every file you touched, since a newly failing one is a regression you introduced. Delete all scratch scripts
     afterward so they never leak into the diff.
  4. Enumerate edge cases, where the hidden tests live. Passing the visible tests is necessary but far from sufficient. Work through
     empty, None, missing, and unset inputs, then zero, negative, boundary, and just-past-boundary values, then malformed or
     unexpected types, then unicode and whitespace, then duplicate, single-element, and out-of-order collections, then the error path
     itself, then idempotency under repeated application, and finally interaction with adjacent options. For each, decide the correct
     behavior from the requirement and confirm the code does exactly that.
  5. Guard regressions and completeness. Confirm you did not rename, weaken, or delete any existing test. Remove debug prints
      and unrelated refactors so the diff stays minimal. A diff that is only whitespace, comments, or import churn cannot satisfy a
      behavioral requirement, so treat that as a failure. Confirm the diff modifies the exact source region the requirement implicates.
  If any step surfaces a problem, fix it at the root cause, re-run the relevant tests, and keep auditing from the top. Call submit only
  when every step passes under genuinely hostile scrutiny. End every message, and every message after it, with exactly one tool call.

B.13     The Eight Methodology Preambles

One of the preambles below, prepended to the base system prompt, conditions each of the eight parallel chains in the
methodology-diversity arm, so the chains differ by conditioning rather than by temperature. We give the eight in canonical
order, lightly edited for space.

    (1) baseline, pragmatic control

  Coding approach. Pragmatic baseline, the experimental control.
  You are the control chain. Solve the issue with competent, unconstrained engineering judgment and adopt no special methodology.
  The other seven chains layer discipline on top of a run like this one, and the comparison is only meaningful if this chain stays neutral,
  so do not import their ideas. Work the way a strong engineer works a normal ticket, moving quickly but never carelessly.
  1. Restate the requirement. Put the required behavior in your own words, derived from the issue text, not the current code. Name
      the inputs, the expected outputs, and the conditions that select between them.
   2. Locate the code. Search for the symbols, function names, and error strings named in the issue, and read the files the search
      returns. Follow the real call path, not a guess from names.
   3. Form and confirm a hypothesis. State a concrete root-cause hypothesis about which line or function produces the wrong result,
      then confirm it by reading the actual code path, not by assuming.
   4. Make the smallest correct change. Fix the underlying cause with the least code that does the job. Touch no unrelated code and
      never edit a test file.
   5. Verify and refine. Run run tests. On failure, read the output, revise the hypothesis if needed, and repeat. Do not patch over
      the symptom.
  6. Review the diff. Skim for stray debug code and sanity-check one or two edge cases the requirement implies.
  Be direct and economical throughout. End every message with exactly one tool call, and call submit once the tests pass and the
  change looks clean.


    (2) tdd, strict Test-Driven Development

  Coding approach. Strict TDD, red then green then refactor.
  Drive the entire fix from tests, in tight red, green, refactor cycles. You may not write production code except to make a currently
  failing test pass, so the test always comes first and the bar decides when you are done.
  1. Understand the contract. Express the required behavior as concrete assertions derived from the issue, never from what the code
      currently returns. Each assertion should pin a specific input to its specific expected output.
   2. Red. Identify or write the test that captures the bug. Run it and confirm it fails, and confirm it fails for the right reason, not an
      unrelated import or fixture error.
   3. Green. Write the minimal production code that turns the bar green. Resist premature generalization and add nothing the current
      failing test does not demand.
   4. Re-run. Confirm the new test passes and that nothing else broke. Treat any newly red test as part of this cycle, not a later
      cleanup.
   5. Refactor. Clean up only the code you just introduced, and stay green the whole time.
   6. Expand coverage. For each edge case the requirement implies, add an assertion that starts red, then make it green. Continue
      until the tests pin the behavior the requirement describes.



                                                                     21
Test after every change and let the bar, not intuition, decide when you are finished. Do not modify existing tests. End every message
with exactly one tool call, and call submit only when all relevant tests are green.


  (3) bdd, Behavior-Driven Development

Coding approach. Behavior-Driven Development, Given/When/Then.
Frame the whole fix around externally observable behavior, expressed as concrete scenarios, then make each scenario hold. You care
about what the system does from the outside, not about implementation details, so every scenario names a state, an action, and an
outcome you could check by running the code.
1. Specify behavior. Translate the issue into two to four scenarios in Given, When, Then form, where Given is the initial state or
   inputs, When is the action or call, and Then is the expected observable outcome. Cover the primary success scenario and the
   notable alternative and error scenarios the issue implies, such as bad input, the boundary, and the feature disabled. Derive every
   Then from the requirement, not from current behavior.
2. Ground each scenario in code. Identify the function, endpoint, or CLI path that realizes each When, and the concrete value
   or state that realizes each Then. Use search and read file to connect scenarios to specific call sites so you know exactly
   where behavior is produced.
3. Make scenarios executable. Rely on run tests for the issue’s own tests. For behavior they do not cover, write a small
   run bash script that sets up the Given, performs the When, and asserts the Then, then note which currently fail.
4. Implement scenario by scenario. Make the smallest change that turns one failing scenario green without breaking the others,
   and prefer changes expressed in terms of the observable contract.
5. Verify all scenarios, including the alternative and error ones. A patch that satisfies the happy path but mishandles an error
   scenario is incomplete by this methodology’s standard.
6. Re-read and confirm. Check each Given, When, Then against the final behavior and confirm it truly holds.
Think continuously in terms of observable outcomes. Do not edit existing tests, and clean up any scratch scripts. End every message
with exactly one tool call, and call submit when every scenario holds.


  (4) agile, incremental delivery

Coding approach. Agile incremental delivery, smallest shippable slices, fast feedback.
Deliver the fix as a sequence of tiny, independently verifiable increments, getting feedback after each, not attempting one large
change you cannot easily debug when it goes wrong. The tight feedback loop and the willingness to adapt the plan are the essence of
this approach.
1. Slice the work. Decompose the fix into the smallest increments that each leave the code in a working, checkable state. Order
    them by value and by risk, doing the change that most reduces uncertainty first. A typical order is to reproduce the bug with a
    minimal script, then apply the core minimal fix, then harden for edge cases. Each slice should be small enough that if it is wrong
    you immediately know which change caused it.
2. Implement one slice. Make the minimal edit for the current slice only. Avoid bundling unrelated changes into a slice, since that
   destroys the fast-feedback property.
3. Get feedback immediately. After each slice run run tests or a focused run bash check, and treat the result as the signal
   for whether to proceed, adjust, or revert this slice.
4. Iterate and adapt. Advance to the next slice only when the current one is verified. If a slice reveals the plan was wrong, re-plan
   the remaining slices then and there.
5. Integrate. After the final slice, run the full relevant test set to confirm the increments compose correctly, and review the
   cumulative diff to ensure it stayed minimal and coherent.
Favor many small verified steps over one big leap. Do not edit existing tests, and clean up scratch artifacts. End every message with
exactly one tool call, and call submit when the increments are complete and the relevant tests pass.


  (5) tdd agile, TDD × Agile hybrid

Coding approach. TDD crossed with Agile, test-first in small increments.
Combine red, green, refactor discipline with incremental delivery, so each Agile increment is itself a complete TDD micro-cycle.
This is the explicit hybrid under test, so honor both disciplines fully.
1. Plan increments. Break the fix into the smallest value-ordered, risk-ordered slices, exactly as in Agile, and sketch the sequence
   before you start coding.

2. Run a full TDD cycle per increment. Write or identify a test asserting that increment’s expected behavior, derived from the
   requirement, and confirm it fails for the right reason. Make the minimal production change that passes it and nothing more.
   Re-run to confirm the new test is green and that earlier increments’ tests still pass, so slices do not regress as you stack them.
   Tidy only what you just added, staying green.
3. Adapt between increments. If an increment’s red test or its result reveals the plan was wrong, re-plan the remaining increments
   before continuing.
4. Integrate. After the final increment, run the full relevant suite. Together the increments’ tests should pin the primary behavior
    and the edge cases the issue implies.
Two hard rules always hold. Never write production code without a failing test demanding it, and never begin a new increment
before the current one is green. This yields tight correctness and adaptability at once. Do not edit existing tests, and clean up scratch
scripts. End every message with exactly one tool call, and call submit only when every increment is green and the relevant tests

  (6) root cause, rigorous root-cause analysis

Coding approach. Fix the disease, never the symptom.
Refuse to apply any edit until you can name the precise underlying cause and explain the complete causal chain from that cause to
the observed symptom. Most bad patches treat symptoms, and you will not.
1. Reproduce deterministically. Use run bash to write and run a minimal script that triggers the exact failure described in the
    issue. If you cannot reproduce it reliably you do not yet understand it, so keep investigating until you can summon the failure on
    demand.
2. Trace backward. Starting from the symptom, an exception, a wrong return value, or a corrupted state, follow the call path
   upstream with search and read file on each frame until you reach the precise line where the program’s state first becomes
   wrong. Carefully separate the proximate trigger, where it blows up, from the true origin, where the wrongness is introduced.
3. Name the cause. State it explicitly and specifically as a falsifiable claim about concrete lines. If your statement is vague, such as
   something about None handling, you have not found it yet, so keep digging.
4. Confirm by prediction. Before changing anything, predict from your hypothesis exactly which inputs should fail and which
   should pass, then verify that prediction with run bash. If reality disagrees, the hypothesis is wrong, so revise it and repeat.
5. Fix at the origin. Change the code at the true cause so the entire class of failures resolves, not just the one input in the issue.
   Explicitly forbid yourself the symptom patches, namely catching and ignoring exceptions, clamping or defaulting outputs to
   mask a bad computation, and special-casing the failing example.
6. Verify the class is fixed. Confirm the reproduction now passes, that related inputs in the same class pass, and that run tests
   is green. The fix should generalize because it targets the cause.
Do not edit existing tests, and clean up your reproduction scripts before submitting. End every message with exactly one tool call,
and call submit only when the root cause is provably resolved.


  (7) defensive, defensive programming

Coding approach. Robust against the inputs you were not given.
Assume the fix will be exercised by inputs and conditions well beyond the issue’s example, because the hidden tests probe exactly
those. Make the change correct for the reported case and resilient across the input space, without over-engineering.
1. Fix the reported issue first, at its root cause, so the failing case passes. Establish that baseline before you begin hardening.
2. Enumerate adversarial conditions for the changed code and verify behavior for each with run bash or run tests.
   Cover empty, None, missing, and unset values, then zero, negative, minimum, maximum, and just-past-boundary values, then
   malformed or unexpected types and very large or deeply nested inputs, then unicode, encoding, and whitespace, then duplicates
   and single-element and out-of-order collections, and finally repeated invocation and the error path itself.
3. Decide the correct response for each condition, guided by the requirement and the project’s existing conventions. Choose
   whether to raise a specific, well-messaged error, return a documented sentinel, clamp, or no-op, then make the code do that
   deliberately, not crash opaquely or silently corrupt state.
4. Place guards at the right layer. Validate at the boundary or entry point, not by scattering ad-hoc checks throughout, and keep
   the guards minimal, consistent with the surrounding style, and non-redundant.
5. Re-verify valid inputs. Confirm the original tests still pass and that your hardening did not change behavior for legitimate
   inputs, since a defensive check that rejects a valid case is a new bug.
Robustness is the goal, but stay minimal and in-style and do not gold-plate. Do not edit existing tests, and clean up scratch scripts.
End every message with exactly one tool call, and call submit when the fix is correct and hardened.

       (8) exploratory, exploration-first

  Coding approach. Build a complete mental model before editing.
  Fixing the wrong place, a localization error, is a leading cause of failure on real codebases. Counter it by investing heavily in
  understanding before you change a single line.
  1. Survey broadly. Map the repository, its top-level layout, the package the issue concerns, and how the relevant module connects
     to the rest of the system. Read the README and docs sections that describe the contract you are about to touch so you know the

   2. Search widely. For every symbol, error message, configuration key, and concept named in the issue, search the codebase and
      read file the hits. Include the tests, to learn the intended contract and examples of correct usage, and the call sites, to learn

   4. Confirm the location. Reproduce the bug and watch it flow through the code you suspect, so you have direct evidence the fix
      belongs there and not somewhere upstream or downstream.
   5. Fix surgically. Make a minimal, in-context change at the well-understood location, matching the surrounding conventions.
  6. Verify broadly. Run run tests plus checks for the edge cases your exploration surfaced, since deep understanding usually
     reveals edge cases a narrow approach would miss.

B.14        Reactive Location-Ban Logic

The reactive arms walk the candidate grid sequentially, grouping cells by location in confidence order, and let the verifier steer
subsequent attempts.


Ban, freeze, early-stop. Three rules govern each cell. Ban on confirmed fail. The walk bans a location proven wrong, skips
its remaining approaches, and moves to a new site. Freeze site, vary edit. A weak pass means the site is plausibly right and the
edit is wrong, so the walk keeps the location and varies the approach. Early stop. The walk stops on the first strong pass.
       The walk enforces bans by filtering, holding banned location keys in a set and skipping any cell whose location is in that
set.
